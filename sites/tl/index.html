QR은 잘 읽히죠.
예뻤던 적이 없을 뿐

포스터·패키지·명함… QR이 안 들어가는 데가 없는데, 공들인 디자인 위에 마지막으로 흑백 네모를 얹는 건 늘 아쉬웠어요. 그런데 QR이 그렇게 생긴 데는 이유가 있습니다 — 1994년의 카메라와 연산으로 «어떻게든 읽히게» 만든 결과거든요.

그 제약이 지금은 많이 풀렸습니다. 카메라도 연산도 넉넉해졌죠. 그래서 인식 성능만 더 쫓는 대신 눈에 들어오는 쪽으로 한번 만들어 봤어요. QR을 대체하려는 게 아니라, 옆자리를 하나 만드는 겁니다. 결과물은 3D 바코드 — 평면에 인쇄되지만 눈에는 입체로 읽힙니다.

코드 만들어보기 GitHub

타입

어디에 얹을지에 따라 고르면 됩니다. 평면 타입은 모두 같은 데이터 계약을 공유하고 실루엣만 달라요. True 3D H는 Y 그룹의 실제 큐브 확장으로, 포맷이 따로 있어요. 아래 코드에는 전부 https://tl.estre.so 가 들어 있어요.

Type Y — 단일 큐브

세 면이 각각 n×n 격자. 한 덩어리라 간판·굿즈에 어울립니다.

n = 13 / 21 / 25 · 순 페이로드 31 / 98 / 141 B

True 3D H — Y 그룹의 실제 큐브 확장

실제 큐브의 면 1…6개에 서로 다른 데이터를 싣는 별도 포맷이에요. 생성기에서 회전 영상(MP4)·종이 도안·3D 인쇄 파일도 받을 수 있어요.

H0…H8 · n = 13…45 · 순 페이로드 3면 3…333 B · 6면 6…666 B (ECC-M · 3톤)

Type O — 육각 필드

가장 기본형. 중앙 파인더를 중심으로 마름모 셀이 깔립니다.

k = 6 / 8 / 10 / 12 · 순 페이로드 18 / 39 / 65 / 97 B

Type C — 3시 노치 초대용량

3시 방향 노치가 실루엣만으로 방향과 타입을 확정합니다. C0~C3는 근접 스캔 전용이며, C1 이상은 가까이 대거나 확대해서 읽어야 해요.

k = 14 / 16 / 18 / 20 · 순 페이로드 130 / 172 / 220 / 255 B

Type A — 삼각 실루엣

육각 코어에 코너 패치를 더해 정삼각형이 됩니다.

k = 6 / 8 / 10 · 순 페이로드 31 / 62 / 101 B

Type K — 육각별

정삼각형과 그 180° 상을 합친 별. 같은 k 에서 용량이 가장 큽니다.

k = 6 / 8 / 10 · 순 페이로드 43 / 86 / 138 B

순 페이로드는 ECC-M 기준이에요. H를 포함한 모든 타입에 폴백 QR 을 함께 인쇄할 수 있어서, TL 코드를 못 읽는 환경에서도 최소한의 경로가 남습니다. H는 기본으로 좌상단 모서리에 QR을 넣어요.

왜 지금인가

QR은 그 시절의 최선이었습니다. 흑백 두 값, 정사각 모듈, 큰 파인더 — 전부 «성능이 빠듯한 카메라로도 읽히게» 하려는 선택이었어요. 그 제약 아래서는 미감을 포기하는 게 합리적이었습니다.

그 전제가 바뀌었어요. 지금 폰 카메라는 그때와 비교가 안 되고, 실시간 영상 처리도 브라우저 안에서 됩니다. 그러면 남는 여유를 밀도에 더 쓸 게 아니라 보이는 것에 써도 되지 않을까 — 그게 이걸 만든 이유입니다.

대신 밀도는 포기했습니다. 마름모 셀은 정사각 모듈보다 면적 효율이 불리해요. 이 포맷은 밀도 경쟁을 하지 않습니다. 많이 담아야 하면 QR이 맞아요.

어떻게 동작하나

1. 셀 = 마름모 3면

육각 셀을 rhombille 타일링으로 T·L·R 세 면으로 나눕니다.

2. 순서 = 심볼

세 면의 휘도에 순위를 매기면 3! = 6가지 — base-6 digit 하나입니다.

3. 3 digit = 1 심볼

GF(211) 소수체 위의 Reed–Solomon 으로 오류를 정정합니다.

무엇이 자유로워지나

단조 변환에 불변합니다. 전역 조명 변화·감마·프린터 톤 매핑처럼 단조 증가하는 톤 변형은 순서를 바꾸지 못합니다. 순서만 보존되면 값이 삽니다.

렌더러가 자유롭습니다. 데이터 계약이 "면 사이의 순서 + 최소 분리폭" 뿐이라, 그 안에서 색·질감·면 그라데이션·애니메이션이 전부 열려 있습니다. 그 자유도가 이 포맷의 핵심이에요.

다만 «자동으로 예뻐지는» 건 아닙니다. 자유로워지는 것은 계약이지 결과가 아니에요. 그 안에서 무엇을 그릴지는 여전히 만드는 사람 몫입니다.

스캐너 개선 현황

디코더는 동작합니다. 네 타입 모두 실기기 사진에서 읽히고, 지금은 인식률과 속도를 끌어올리는 개선 단계예요. 아래 시간은 실기기 촬영 정지사진 한 장을 한 번 복호한 값이며, 라이브 첫 잠금 시간이나 성공률이 아니에요.

타입실사진 복호정지사진 1회 복호라이브 검증
Type Y — 단일 큐브9 / 16약 1.8초추가 측정 중
Type O — 육각 필드29 / 48약 1.9초추가 측정 중
Type A — 삼각 실루엣18 / 19약 2.4초추가 측정 중
Type K — 육각별18 / 27약 3.1초추가 측정 중
중앙 QR 변형 (네 타입 공통) · 2026-08-138 / 9—추가 측정 중

정지사진 한 장을 한 번 읽는 기준입니다. 지금은 Type O가 가장 짧고 A·K·Y가 비슷하게 더 깁니다. ⚠ 이전 게시에서 «Type Y가 가장 빠르다»고 적었던 것은 사진 9장 기준이었고, 표본을 넓혀 다시 재니 순서가 뒤집혔어요. 이 수치를 라이브 첫 잠금 시간으로 읽으면 안 됩니다.

정지사진 1회 복호 시간만으로 라이브 체감을 예측할 수 없습니다. 시험판의 초기 실기기 계측에서는 한 프레임을 빨리 처리해도 성공까지 많은 프레임이 필요하면 첫 잠금이 늦어졌고, 타입 순위도 정지사진 표와 달라졌어요. 아직 기기 한 대의 작은 표본이므로 라이브 등급은 붙이지 않고 추가 측정 중으로 표시합니다.

촬영 조건도 크게 작용합니다. 실측에서 셀당 9픽셀이 복호 하한이었고, 같은 거리라도 초광각 렌즈로 찍으면 코드가 작게 담겨 이 선 아래로 내려갔어요 (초광각 7.6px 실패 / 광각 9.1px 성공). 스캐너에 렌즈 선택을 넣어 둔 이유입니다.

중앙 QR 변형은 QR 블록이 중앙 파인더 자리를 대신하고, QR의 파인더를 위치·방향 진입점으로 써서 바깥 TL 본문을 복호해요. QR은 기본적으로 리더 링크를 담는 폴백이고, 실제 페이로드는 TL 본문에 남습니다. 2026-08-28부터 Type O·C·A·K 생성기의 기본값은 중앙 TL 파인더와 바깥 좌상단 모서리의 폴백 QR이고, 중앙 QR은 파인더 선택지 중 하나로 남아 있어요. 위 표의 중앙 QR 행은 이 변형을 잰 2026-08-13 라운드 값이에요.

Type C와 True 3D H는 위 표에 포함되지 않으며, H의 실카메라 인식률이나 FPS는 보장하지 않아요. 스캐너에는 엔진이 둘 있어요: R1은 평면 TL 타입을 프레임 한 장씩 읽고, 기본 엔진인 R2는 Type Y와 H를 여러 프레임에 걸쳐 모아 읽어요. H는 필요한 면을 모아 RS/CRC 검증을 통과한 뒤에만 결과를 보여줘요. BarcodeDetector를 지원하는 브라우저에서는 R2가 일반 QR 코드도 읽고, QR에서 읽은 링크는 자동으로 열지 않아요 — 주소를 확인한 뒤 직접 눌러 열어요.

측정 2026-08-27 · 표본 110장 (각 장을 960 · 1440px 두 해상도로 시도). ⚠ 표본은 대부분 모니터 화면을 찍은 사진이라 인쇄물·실배치 수치가 아니에요. 그리고 코퍼스 233장 중 123장은 «지금 못 읽는 것»을 일부러 모아 둔 한계·실험 프레임이라 성능 표본에서 뺐습니다. 중앙 QR 행만 2026-08-13 옛 라운드 값이에요.
