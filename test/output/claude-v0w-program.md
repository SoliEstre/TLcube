## 3. 과업 ② — v0 계열 전제 최적화

프로파일이 가리킨 곳은 «후보 수» 다음으로 **원판 표본 주변의 순수 오버헤드**였다.
둘 다 **결과를 바꾸지 않는** 변경만 골랐다 (게이트·문턱·알고리즘 무접촉).

### O1. 정규화 H · 역행렬의 H-정체성 메모이즈 (`grid-sample.js`)

`sampleProjectedDisc` 는 원판마다 `normalizeHomographyScale(H)` +
`invertHomographyInternal(...)` 를 다시 돌리고 `Float64Array` 두 개를 새로 만들었다.
둘 다 **H 만의 함수**인데 한 레이아웃 평가는 같은 H 로 원판을 n²×3면
(21² × 3 = 1,323) 표본한다. `WeakMap<H, {normalized, inverse}>` 로 메모이즈했다.

- 값이 같은 **다른** H 객체는 각자 계산한다 (정체성 키) → 부동소수 결과 동일
- 전제 «H 는 만든 뒤 제자리 변경 없음» 은 기존 `homographyCacheKeys` 가 이미 세워 둔 것

### O2. 원판 캐시 키를 문자열 → 중첩 Map (`grid-sample.js`)

원판 키가 `String(x)+'|'+String(y)+'|'+String(radius)` 였다. 배정밀도 → 문자열이
원판당 3회이고 원판 수는 레이아웃당 n²×3면이다 (프로파일 `cacheNumberKey` 4.5 %).
`config → x → y → radius` 4단 Map 으로 바꿔 문자열을 아예 안 만든다.
곁들여 `ok({...})` 전개를 고정 모양 리터럴(`wrapDiscSample`)로 바꿨다
(프로파일 `contracts.ok` 3.2 % · 히든클래스 단일화).

- 유일한 의미 차이: Map 키는 SameValueZero 라 `-0` 과 `0` 이 **같은 칸**을 쓴다.
  두 값은 이후 연산에서 비트까지 같은 결과를 내므로 같은 칸이 옳다. NaN 은
  `validateDisc` 가 먼저 막는다.
- 캐시 히트도 **매번 새 객체**를 돌려준다 (별칭 사고 방지 — 공유 객체 반환 안 함)

## 9. 한 줄 결론

**과업 ①** v1r2 · v2r2 를 검출 라인업(블록 로케이터 패밀리 · CS 평가 후보)과 생성기
카드에서 내렸다. 와이어·정본·판독은 그대로이고, 스위치 세 개면 드랍 전 상태가
그대로 돌아온다 (그 사실을 테스트가 매 실행 증명한다). n=25 는 **Y2 공백**이 됐다.

**과업 ②** 프로파일이 지목한 곳은 «후보 수 × 원판 표본» 이었다.
드랍(후보 축) + H 정규화·역행렬 메모이즈(O1) + 원판 캐시 키 탈문자열화(O2) 로
**프레임 중앙값이 v0 38.0 % · v0X 40.6 % · v0XQ 49.5 %** 로 내려갔다 — 세 타깃 모두
목표선(절반)을 넘겼다. 정본 스위트 실행 시간은 161.7 → 100.8 s, 실사진 경로는
213.4 → 107.3 s 다.

**정확도**: 49-매트릭스 비트 동일 · cell_px 스윕 불일치 0/540 · 실사진 덤프 성공
92/149 동일 · 실사진 핀 동일(기준선의 빨간 1건 그대로). **게이트는 한 값도 안 건드렸다.**

**남은 병목**: `sampleProjectedDisc` 본체(32 %)와 실루엣 전처리(≈ 7.6 %).

### 10.2 유도 — 70/70 셀 완전 일치, 손 좌표표 0

`normalizeMidFaces` 가 결정적으로 2 를 채우고, 그 값이 v1r2 NW 의 (0,4)=(2,2,2) 와
같다 — 즉 **손이 고른 값은 하나도 없고 v0W 정본의 mid 면은 0개**다.

### 10.3 정정 — 「R면 반전」은 반전이 아니다

팩 `_note` 는 「SE 3×3 R 반전 = 위상 마커」라고 적었다. 실측 무늬는:

```
T          L          R
2 2 2      2 2 2      0 0 0
2 0 0      2 0 0      0 2 0
2 0 0      2 0 0      0 0 0
```

비트 반전이면 R 이 `000 / 022 / 022` 여야 한다. 실제 R 은 **중앙 1점**이고,
T·L 은 상단행+좌열 **L자**(밝음 5)다. 이 무늬의 출처는 **v0 정본의 SE 코너 블록
그대로**다 ((10..12)² → (+8,+8)). 즉 「반전」이라는 서술보다 「v0 코너를 그대로
가져왔다」가 정확하고, 후자는 «작아도 읽히는 이력» 이라는 근거까지 딸려 온다.
문서·주석·테스트는 **잰 쪽**을 적었다.

### 10.4 회계 (autoplace 재산출 — 팩의 counts 를 안 믿는다)

```

```

레거시(포맷 v1) 세대는 **없다** — v0xq 전례와 같이 포맷 v2 전환 이후 신설이라

- 기대 패널: `v0W` 버튼 추가 (값은 레이아웃 id 소문자 `v0w`).

### 11.2 로케이터 — **가장 중요한 실측 하나**

`anchoredSimilaritySeed` 는 «면 T 의 원거리 코어가 canonical **(0,−1)**·r 에 있다» 를
전제한다. v0·v0X·v1r2·v2r2 는 원거리 블록이 **먼 꼭짓점**(C0·C2·C4)이라 그 전제가
참이다(실측 θ = −90.0°). v0W 의 NE 동심 사각은 **심(seam) 꼭짓점**(C1·C3·C5)이라
**θ = −141.1°** 다 — 그대로 쓰면 51.1° 틀어진 시드가 나온다
(`test/output/lanes/claude-v0w-probe-geom.mjs` 실측).

그래서 canonical 앵커 방향을 받는 **일반형** `anchoredSimilaritySeedTo` 를 신설했다.
`p̂ = (0,−1)` 을 넣으면 기존 특수형과 **정확히 같은 식**이 되고, 그 포함관계를
테스트가 h0..h8 비트 단위로 단언한다. 기존 호출부는 **한 줄도 안 바꿨다** —
연산 순서가 달라지면 기존 패밀리 포즈가 흔들릴 수 있고 이 레인의 합격선은 무회귀다.

### 11.3 v0X 와는 **시드에서 안 갈라진다** (정직하게)

| | v0X | v0W |
|---|---|---|
| 동심 사각 블록 | SE (15..20)² | NE (0..5)×(15..20) — **같은 블록의 평행이동본** |
| 코어 반경 | 18.0셀 | **16.7033셀** (√279) |
| 사각 링 동반자 | 있다 (3면 동일) | **있다** (3면 동일) |
| 중앙 | K3 불스아이 | K3 불스아이 |

반경 차 1.30셀은 `ANCHOR_SNAP_CELLS`(3.2) 안이고 동반자 게이트도 양쪽 다 참이다 —
**두 패밀리는 서로의 프레임에서 서로 시드된다.** 실측이 그렇다: v0X 프레임에서
v0w 포즈 245개(49프레임 합), v0W 프레임에서 v0x 포즈 109개.

가르는 것은 **패치 Pearson + 하류 CS 수용 게이트(0.78 · 0.035)** 다.
그리고 **교차 오수용은 0 이다** (§12.2). v0xq 편입에서 확인한 것과 같은 구조다.

> ⚠ 부수 효과 하나를 기록한다: v0X 의 사각 링 게이트 실패 경로가 예전에는
> `continue` 로 **코너 반복 자체**를 끊었다. 그때는 뒤에 아무 패밀리도 없어 결과가
> 같았지만, v0W 가 뒤에 붙으면 «v0X 게이트가 v0W 를 대신 자르는» 결합이 생긴다.
> 중첩 if 로 끊었다 — 기존 패밀리 동작은 비트 단위로 동일하다(뒤에 코드가 없던
> 자리의 형태 변경). §12.3 비침습성 대조군이 그것을 매 실행 증명한다.

  즉 **얇은 마진으로 틀린 위상이 수용되고 데이터가 통째로 어긋난다.**

**시간 비용의 진짜 출처**는 로케이터가 아니다. v0 프레임(v0w 포즈 0)에서도
+53 % 가 났고 로케이터 단독 시간은 79 → 76 ms 로 거의 같았다. 늘어난 것은

> ⚠ **이것은 합성 예비판이다.** 운영자의 신설 근거는 «v0XQ 실기기 선전에서 얻은

## 16. 첫 판정 — **둘은 같은 종류의 물건이 아니다**

브리프는 «파생 2종» 을 나란히 놓았지만, 회계를 재 보면 한쪽만 와이어에 새 id 를
만든다. 그 갈림이 이 과업의 첫 결과이고 나머지 전부의 전제다.

| | v0WY | v0WQ |
|---|---|---|
| QR 이 앉는 곳 | 실루엣 **밖** (T 면 평면 연장) | 중앙 슬롯 (셀 격자 **안**) |
| 먹는 데이터 셀 | **0** | 64 (+ 중앙 K3 25셀도 함께 사라진다) |
| 셀 집합 | **v0W 와 비트 동일** | 새 집합 (45셀) |
| 와이어 id | **없다** | `v0wq` |
| 로케이터 패밀리 | **없다** (v0W 그대로) | 신설 (v0xq 코너 삼중점 경로 공유) |
| n=21 CS 후보 | 안 늘어난다 | 3 → **4** |
| 생성기에서 고르는 곳 | **QR 위치 카드** `면` | 검출기 카드 `v0WQ` |

### 16.1 v0WY 에 id 를 주지 않은 이유 — 브리프가 스스로 답한다

브리프의 합격선에 «교차 오수용 — v0W·v0X·v0XQ·O/A **전 방향 0**» 이 있다.
v0WY 를 별도 레이아웃 id 로 만들면 그 셀 집합이 v0W 와 **한 칸도 다르지 않으므로**
디코더가 둘을 가를 근거가 0 이다 — 교차 오수용이 «0» 이 아니라 **설계상 100 %** 가
된다. 게다가 후보가 하나 더 늘어 과업 ① 이 지렛대로 지목한 «(shape × n ×
orientation × seed) × 레이아웃 후보» 곱에 곧바로 얹힌다.

그래서 v0WY 는 **렌더 선택**으로 넣었다: `qrPosition: 'plane'` → `sceneY` 의
`outerFaceQr`. 「데이터 무손실」이라는 지시가 곧 「와이어가 같다」이고, 와이어가
같으면 id 를 만들 자리가 없다. 이 부재 자체를 회귀가 고정한다
(`cellSurfaceFinal.test.js` «v0WY 는 와이어 id 가 아니다» · `locatorY.test.js`
«`cell-surface-v0wy` 는 목록에 없다» · `cellSurface-block-locator.test.js`
«`poseCount.v0wy` 키가 생기면 실패»).

맞는 바이트 수가 없다 (54 B → 56심볼 · 55 B → 58심볼). `decode.finishProfile` 이
그 조합을 «이 포맷은 현행 인코더가 생성할 수 없다» 로 거부한다.

그 게이트를 **손대지 않고** 슬롯을 한 칸 내렸다 → **m = 8**. 부수 효과 둘이 그대로
대조표의 재료다:

- **payload 가 늘어난다** — 83/71/56 B 대 v0XQ 의 80/67/54 B (data 302 대 288).
- **QR 모듈이 잘아진다** — 피치 8/29 = **0.2759셀** 대 v0XQ 의 9/29 = 0.3103셀
  (−11.1 %). 중앙 QR 자체의 실기기 가독성은 v0XQ 보다 **불리**하다.

즉 v0WQ 의 자리는 «데이터를 더 싣고 중앙 QR 은 더 잘게» 다. 이 교환은 이 레인이
고른 것이 아니라 **두 계약이 정한 것**이다 (autoplace 사분면 규칙 + 인코더 청크 정합).

### 17.3 회계 (autoplace 재산출 · 팩 없음)

```
441 − painted 45 − slot 64 − reference 12 − format 18(v2) = data 302 · S = 100 · 잔여 2
```

레거시(포맷 v1) 세대는 **없다** — v0xq · v0w 와 같은 신설 규칙
(`cellSurfaceFinal(21,'v0wq',1)` 은 RangeError). `hasLegacyFormatWire('v0wq') === false`.

## 18. v0WY — 레이아웃 정의·회계

**정의가 곧 «없음»** 이다. 셀 집합·회계·와이어가 v0W 와 문자 그대로 같다:

```
441 − painted 70 − slot 0 − reference 12 − format 18 = data 341 · S = 113 · 잔여 2
```

payload 94 / 80 / 64 B (L/M/H) — v0W 와 **같은 값**. 「데이터 무손실」이 이 등식이다.

### 18.1 기하 — 윈도 β 문법을 좌표만 밖으로

T 면 파라메트릭 (a,b) 에서 **a=b=n 이 면의 먼 꼭짓점 C0** 다 (T 기저의 합이 (0,−1)).
그 너머는 실루엣 밖이고 다른 면도 없다. 그래서:

| | 윈도 β (`inner`) | 면-평면 QR (`plane`, v0WY) |
|---|---|---|
| 좌표 | a,b ∈ [n−13, n] (면 **안쪽**) | a,b ∈ [n+1, n+15.5] (**바깥쪽**) |
| 데이터 셀 손실 | 13×13 | **0** |
| L/R 필러 | 필요 (세 면 공통 배제 구멍) | **불필요** (메울 면이 없다) |
| 콰이어트 | 안쪽 4모듈 + 바깥 2변은 배경 | 블록 전체 콰이어트 패치 (4변) |
| 모듈 피치 | 데이터 피치 ½ | **같다** (½) |
| 방향 | 정렬 패턴 코너가 Y-심 쪽 | **같은 뒤집기** |
| 지원 n | 25 (Y2) 전용 | **전 레이아웃** (셀 격자를 안 건드린다) |

화면에서는 **마름모**가 된다 — 가로 대각 √3·side, 세로 폭 side, 중심 x 는 큐브와 같다.
`renderWindowQr` 를 **호출하지도 수정하지도 않는다** (renderCenterQr 이 세운 규율과
같다 — 기하가 다르고, 기존 윈도 β 렌더 계약을 한 도형도 흔들지 않기 위해서다).

### 18.2 «무손실» 의 진짜 비용 — **데이터가 아니라 면적**

QR 블록은 콰이어트 포함 29모듈 = **14.5셀**이고 큐브와 1셀 띄운다 →
**여백 15.5셀**을 요구한다 (`PLANE_QR_MARGIN_CELLS`). 기본 margin 이 20셀이라
평소에는 아무것도 안 바뀌지만, **같은 인쇄 면적**에서는 큐브가 그만큼 작아진다.
그래서 아래 벤치는 셋을 **같은 ppu · 같은 margin · 같은 캔버스**로 맞춰 잰다 —
안 그러면 «셀이 작아 못 읽은 것» 을 «QR 이 방해한 것» 으로 오독한다.

margin 이 모자라면 **조용히 잘리지 않고 throw** 한다 (코너 QR 겹침 가드와 같은 규율).

## 19. 로케이터

### 19.1 v0WQ — v0XQ 의 **코너 삼중점 경로를 공유**한다

v0WQ 는 중앙 K3 가 없다 (슬롯이 가져갔다). 그래서 v0W 가 타는 앵커드(중앙 × 원거리)
시딩이 성립하지 않고, **v0xq 와 같은 경로**를 탄다 — 3코너 동심 사각의 120° 삼중점이
중앙·스케일·위상을 동시에 주고, **중앙 QR 블록이 제4 앵커**다
(브리프의 «중앙 QR 앵커는 v0xq 모델 공간 전례» — `buildCenterQrPatch` 를 슬롯 한 변만
바꿔 그대로 쓴다. `detectQrFinderTriples` 를 부르지 않는 것도 그대로다: import 순환).

**공유의 정도가 이 절의 핵심이다.**

| | v0XQ | v0WQ |
|---|---|---|
| 코너 블록 | (0..5)×(15..20) | **같은 셀·같은 톤** |
| 코어 반경 | √279 = 16.7033셀 | **같다** |
| 코너 검증 순회 | `verifyV0xqCornerCluster` | **같은 배열을 재사용** (다시 안 훑는다) |
| 삼중점 탐색 | 같은 코너 배열 | **같은 배열** |
| 중앙 앵커 | 중앙 QR 패치 (슬롯 9) | 중앙 QR 패치 (**슬롯 8**) |
| 서브앵커 | 코너 3 + SW 마커 3 | 코너 3 + **SE 마커 3** |

즉 **시드 단계에서 안 갈라진다** — v0X ↔ v0W 에서 겪은 것과 같은 구조다(§11.3).
가르는 것은 ① 중앙 QR 패치(슬롯 크기가 달라 콰이어트 프레임 셀 집합이 다르다)
② 위상 마커 서브패치 ③ 하류 CS 게이트(0.78 · 0.035)다. **게이트는 안 건드렸다.**

구현은 `assembleV0xqPoses` 를 레이아웃 인자를 받는 `assembleCentreQrPoses` 로 일반화하고
특수형 두 개(`assembleV0xqPoses` · `assembleV0wqPoses`)를 그 위에 얹었다.
**기존 호출 형태는 한 줄도 안 바꿨다** (내부 노출·테스트가 그 이름으로 걸려 있다).

편입 비용은 «코너 재탐색» 이 아니라 **«삼중점당 중앙 게이트 + refinePose 한 벌»** 이다.
진단에 `centerQr.v0wqTripleCount` 를 따로 실어, 두 패밀리의 삼중점 수가 갈리면
(= 누가 코너 배열을 건드렸으면) 회귀가 즉시 잡는다.

> ⚠ **부수 계약 변경 하나** — 코너 수집 순회의 게이트가
> `v0xqFamily !== false` 에서 `v0xqFamily !== false || v0wqFamily !== false` 로 넓어졌다.
> 그래서 «v0xq 만 끄면 코너 검증이 0» 이던 기존 단언이 더 이상 참이 아니다
> (둘 다 꺼야 0). 침습이 아니라 **공유**이며, 기존 패밀리의 `verified` ·
> `poseCount` 는 on/off 로 **전부 동일**하다 — 그 사실을 갱신된 대조군이 매 실행 잰다
> («둘 다 끔» 팔을 추가했고, 켠 쪽·한쪽만 끈 쪽·둘 다 끈 쪽 셋을 나란히 단언한다).

### 19.2 v0WY — **로케이터가 없다** (v0W 서명 그대로)

바깥 QR 은 셀 격자 밖이라 파인더 정본에 한 셀도 더하지 않는다. 로케이터는 v0W 의
서명(K3 중앙 × 심 꼭짓점 동심 사각 × SE 위상 마커) 그대로이고, 새 패밀리도 새
`poseCount` 키도 없다.

**그런데 «없다» 가 «무해» 는 아니다.** QR 은 밝은 콰이어트 패치 안에 **암 코어를 가진
정사각 파인더 3개**를 담고 있고, 그것은 CS 블록 로케이터의 동심 코어 스캐너가 찾는
바로 그 무늬다. 실루엣 밖에 그 무늬가 놓이면 ① Otsu 문턱이 밀리고 ② 코어 후보 상위
슬롯을 가짜가 먹는다. §21.2 가 그 비용을 **코너 QR 과 나란히** 잰다.

읽기:

- **2톤에서 v0WQ 는 v0XQ 보다 정확하고(49 대 48) 빠르다(750 대 937 ms).**
  귀속은 위상 마커다 — v0XQ 의 SW 6셀 대신 v0W 의 SE 3×3 9셀이 120° 위상을 지고,
  면 비대칭 셀 비율이 **6/42 = 14.3 % → 9/45 = 20.0 %** 로 두꺼워진다.
  §12.6 에서 v0W 가 v0X 에 진 이유(«위상 판별력이 얇다»)의 **정확한 반대편**이다:
  중앙을 QR 에 내주면 파인더 총계가 줄어드는 만큼 마커 비율이 올라간다.
- **3톤에서는 시간이 뒤집힌다** (919 대 884). 두 레이아웃 다 49/49 라 정확도는 무승부고,
  v0WQ 가 조금 느리다. 3톤은 면 순위 채점이 무거워 «후보를 하나 더 세우는» 비용이
  그대로 드러나는 구간이다.
- **교차 오수용은 2톤·3톤 전 칸에서 0 이다** (4 타깃 × 49 × 2 = 392 칸).
  v0XQ ↔ v0WQ 는 코너 시드를 공유하므로(§19.1) 포즈 수준에서는 서로 선다 —
  실제로 v0XQ 프레임에서 `v0wq` 포즈 50\~67개, v0WQ 프레임에서 `v0xq` 포즈 50\~55개다.
  **수용은 한 건도 새지 않는다.** 막는 것은 손대지 않은 CS 게이트(0.78 · 0.035)다.

### 21.2 v0WY — **QR 3택 대조군** (같은 기하에서)

v0WY 의 QR 은 큐브 밖이라 데이터를 안 먹지만, **여백을 15.5셀 요구**한다. 그래서
「무해한가」를 재려면 셋을 **같은 ppu · 같은 margin · 같은 캔버스**로 맞춰야 한다
(안 그러면 «셀이 작아 못 읽은 것» 을 «QR 이 방해한 것» 으로 오독한다).
조건: ppu 11 · margin 20셀 · 960² · 2톤 · 49칸. 레이아웃은 셋 다 **v0W**.

| 프레임 | QR | 복호 | 총 ms 중앙값 |
|---|---|---|---|
| `v0w@11` | **없음** | **45/49** | 691 |
| `v0wc` | **코너 QR** (현행 기본 배치) | **26/49** | 873 |
| `v0wy` | **면-평면 QR** (v0WY) | **42/49** | 716 |

**이 표의 결론은 v0WY 가 아니라 코너 QR 이다.**

- 면-평면 QR 의 비용은 45 → 42 (−3칸, −6.7 %). 실루엣 밖 밝은 콰이어트 패치가
  Otsu 문턱을 밀고 QR 파인더 3개가 동심 코어 후보 상위 슬롯을 먹는다.
- **같은 QR 을 코너에 두면 45 → 26 (−19칸, −42.2 %)** 이다. 실패 이유에
  `frontend:symbol-clipped` 가 8건 나타난다 — 코너 블록이 전경 마스크에 붙어
  실루엣이 커지고 큐브가 «잘린 것» 으로 판정된다. 면-평면 QR 에서는 그 실패 종류가
  **한 건도 없다**(전부 `no-format-candidate`).
- 즉 **v0WY 는 «QR 을 다는 방법» 중 지금 있는 것보다 덜 해롭다.** 그리고 이것은
  v0WY 만의 이야기가 아니다 — **현행 생성기 기본값이 코너 QR** 이므로, 실기기에서
  발행되는 대부분의 프레임이 위 26/49 쪽 조건에 가깝다. 이 레인의 배제 목록 밖이라
  손대지 않았지만, **별건으로 올릴 값어치가 있는 관측**이다 (§24 N5).

> ⚠ 정직하게: 이 표는 «QR 이 있으면 성공률이 떨어진다» 를 재는 것이지 «v0WY 가
> v0XQ 보다 낫다» 를 재는 것이 아니다. 세 행 모두 레이아웃이 v0W 이고 ppu 가
> 11 이라 §21.1(ppu 15)과 **직접 비교할 수 없다.** 두 표를 겹쳐 읽지 말 것.

### 21.3 편입 비용 — **다이어트 이득을 까먹었나**

같은 프로세스에서 `shipped` 와 `no-derived`(v0W · v0WQ 를 로케이터·CS 후보 양쪽에서
제외 = 과업 ① 종료 시점)를 나란히 잰다. 타깃은 라인업 기본인 **v0X**다.

| 구성 | n=21 CS 후보 | 복호 | 총 ms 중앙값 | 로케이터 ms |
|---|---|---|---|---|
| `no-derived` (v0W·v0WQ 없음) | 2 | 49/49 | **494** | 96 |
| `shipped` (둘 다 편입) | 4 | 49/49 | **651** | 126 |
| Δ | +2 | 0 | **+157 ms (+31.8 %)** | +30 |

**다이어트 이득을 까먹었나 — 20.2 % 를 돌려줬고 79.8 % 는 남았다.**

기준선(과업 ① 전) 1272 ms → 다이어트 후 494 ms(이 런의 `no-derived`) → v0W·v0WQ
편입 후 651 ms. 다이어트가 번 **778 ms 중 157 ms(20.2 %)를 되돌려줬고**, 기준선 대비는
여전히 **51.2 % (−48.8 %)** 다. «프레임 중앙값 절반» 선은 지켰다.

> 이 표의 두 행은 **같은 프로세스·연속 실행**이라 CPU 조건이 같다. 반면 1272 는
> 과업 ① 의 다른 런에서 온 값이므로 그 비교는 ±5 % 를 감안해 읽어야 한다
> (교차 검증: 이 런의 `no-derived` 494 ms 는 §3.1 의 다이어트 후 516 ms 와 4.3 % 차이다 —
> 두 런이 같은 자리를 가리킨다).
>
> ⚠ **v0W 몫과 v0WQ 몫은 이 레인이 가르지 못했다.** `no-derived` 는 둘을 함께 끈다.
> 가르려면 `--variant shipped,no-v0w,no-v0wq` 3팔을 한 프로세스로 완주시키면 된다
> (하네스에 축은 이미 있다). 조건부 드랍이 v0X·v0XQ 를 내리면 후보가 다시 2 로 돌아가
> 이 비용은 **전부 회수된다** — 과업 ① 이 «후보 수» 를 지렛대로 지목한 것과 같은 축이고
> 부호만 반대다.

- 3톤 속도(−3.8 %)는 «후보가 하나 더 있다» 의 값이므로 **조건부 드랍이 실행되면
  사라진다** (v0XQ 를 내리면 후보가 다시 3 으로 준다).
- 중앙 QR 모듈 −11.1 % 는 **구조적이고 남는다.** 그리고 이 축은 합성이 못 재는
  축이다 — 중앙 QR 은 TL 디코더가 아니라 **일반 QR 리더**가 읽는다. 실기기에서
  「v0WQ 의 중앙 QR 이 카메라로 읽히는가」가 조건부 드랍의 실제 관문이다.

> ⚠ **이것은 합성 예비판이다.** 운영자의 판정 기준은 실기기다(«v0WY/v0WQ > v0XQ →
> v0XQ 드랍»). 이 표의 쓸모는 «어디를 볼지» 를 좁히는 것이고, 좁혀진 두 곳은
> ① **v0WQ 중앙 QR 의 일반 QR 리더 가독성** (모듈이 11 % 작다)
> ② **v0WY 의 면-평면 QR vs 코너 QR** (합성에서 45→42 대 45→26 — 실기기에서 뒤집히는지)
> 다. 나머지 축은 합성에서 이미 v0WQ 쪽이다.

## 25. 과업 3 한 줄 결론

**둘은 같은 종류의 물건이 아니다.** v0WQ 는 셀 집합이 달라 와이어 id 를 얻었고
(`v0wq`), v0WY 는 QR 이 실루엣 **밖**이라 셀을 한 칸도 안 먹어 **id 를 얻지 않았다** —
브리프의 «데이터 무손실» 이 곧 «와이어가 v0W 와 비트 동일» 이고, 그러면 디코더가
둘을 가를 근거가 0 이라 새 id 는 교차 오수용 100 % 를 설계하는 짓이 된다.
그래서 v0WY 는 **QR 위치 카드**(`qrPosition: 'plane'`)로 넣었고, 그 부재 자체를
회귀 넷이 고정한다.

**v0WQ 의 정본은 또 유도다** — NE 동심 사각 36 = `V0XQ_CORNER_CELLS` **같은 배열** ·
SE 위상 마커 9 = `V0W_PHASE_CELLS` **같은 배열**. 손 좌표표 0줄이고, 자기검증 ①-e 가
**참조 동일성**으로 묶어 출처가 시프트하면 로드 시점에 터진다.
슬롯은 **두 번 물어서** 정해졌다: autoplace 상한 9 → 그 안에서 **인코더 정합 ⑤ 가
9 를 거부**해 **8**. 게이트를 안 건드린 결과가 오히려 payload 증가다 (83/71/56 대
v0XQ 의 80/67/54 B).

**로케이터는 v0XQ 의 코너 삼중점 경로를 공유한다** — 동심 사각이 같은 배열·같은
