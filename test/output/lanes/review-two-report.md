**두 건은 충돌하지 않는다.** 둘 다 걸면 daehan 8/8 · 기존 14 통과수 불변 (44) ·

## 2. 건① — 반경 → 파라미터 사상

### 2.1 왜 반경이 아니라 «도달거리» 인가 (실측)

직전 라운드는 각도 오차 δ 가 가장 먼 셀을 `R·√3·cellPx·δ` 만큼 민다고 썼다. 계수 √3 은
**hex 거리 R 인 셀 중 가장 먼 것**을 가정한 값인데, 실제 발자국은 그 원을 다 안 채운다:

| 발자국 | R | 셀 | 최원 셀중심 | 계수 | **reach** (표본점 최대 원점거리) | ρ = reach/reach₁₉ |
|---|---|---|---|---|---|---|
| 기존 19셀 | 2 | 19 | 3.464 | 1.732·R (= √3) | **4.2673** | **1.0000** |
| derived-r6 (파생) | 6 | 39 | 9.644 | 1.607·R | 10.4886 | 2.4579 |
| daehan-79 | 10 | 79 | 15.395 | **1.539·R** | 16.2730 | 3.8134 |

daehan 의 hex 거리 10 짜리 셀들은 육각 «모서리» 방향에 몰려 있어 √3·R (= 17.32) 이
아니라 15.40 이다 — **12% 과대 추정**. 그래서 R 의 함수로 쓰면 반경 2 에서 상수 재현이
어긋난다. 발자국의 표본점에서 **직접 재는** `reach` 를 쓰면 그 문제가 사라진다.

**허용 이동량 κ 의 유도** — 조대 격자의 최대 각도 오차는 반스텝이므로
「가장 먼 표본점의 이동 ≤ κ 셀」은

```
(step/2)·(π/180)·reach ≤ κ      ⇔      step ≤ 360·κ / (π·reach)
```

κ 를 **«현재 기본값이 기존 19셀에서 사는 만큼»** 으로 고정하면

```
κ = (15/2)·(π/180)·4.2673 = 0.5586 셀
```

즉 **«가장 먼 표본점이 반 셀 남짓 안에서 움직인다»** 가 현재 15° 가 담고 있는 조건이다.
이 κ 를 반경과 무관하게 유지하라는 요구가 곧 `step ∝ 1/ρ` 다.

### 2.2 공식 (복사 가능한 JS)

```js
/** 발자국의 «도달거리» — 표본점의 최대 원점거리 (셀 단위).
 *  각도 오차가 미는 거리가 정확히 여기 비례한다. 기존 19셀에서 4.2673. */
function footprintReach(faceSamples) {
  let out = 0;
  for (const sample of faceSamples) {
    for (const point of sample.detailPoints) {
      const d = Math.hypot(point.x, point.y);
      if (d > out) out = d;
    }
  }
  return out;
}
const BASE_REACH = footprintReach(FACE_SAMPLES);   // 4.267317658670374

/** 반경 → 탐색 파라미터. ρ = 1 (기존 19셀) 에서 **한 값도 안 바뀐다**. */
function searchParamsFor(cfg, faceSamples) {
  const rho = footprintReach(faceSamples) / BASE_REACH;
  return {
    ...cfg,
    // 각도: 「가장 먼 표본점의 이동 ≤ κ」 에서 유도 — ρ 에 반비례
    coarseAngleStepDegrees: cfg.coarseAngleStepDegrees / rho,
    // 개수: 각도 가설이 ρ 배로 늘었으니 통과 «비율» 을 유지 — ρ 에 비례
    maxCoarseCandidates: Math.max(1, Math.round(cfg.maxCoarseCandidates * rho)),
    maxRefinedCandidates: Math.max(1, Math.round(cfg.maxRefinedCandidates * rho)),
    // 분산 창: 분산의 봉우리가 발자국 «중심» 에 서려면 발자국을 덮어야 함 — ρ 에 비례
    varianceWindowRadiusCells: cfg.varianceWindowRadiusCells * rho,
    // 분산 보폭: 씨앗이 정교화의 중심 보정 예산(≈0.51셀, 반경 무관) 안에 들어와야 함
    //   → 기하는 ρ⁰ 를 요구하고, 실측이 ρ^0.25 를 고른다 (§2.4 주)
    varianceStepCells: cfg.varianceStepCells * Math.pow(rho, 0.25),
  };
}
```

**그리고 이건 그룹별로 돌려야 한다** — `detectCellFinders` 의 조대 루프를
`groupByFootprint` 로 쪼개고 각 그룹이 자기 `searchParamsFor` 로 자기 각도 격자를 돈다.
그래야 반경 2 후보가 반경 10 때문에 비싸지지 않는다 (§2.5).

이 공식이 반경별로 내놓는 값 (실측 출력):

| 발자국 | ρ | angle | coarse | refined | win | vstep |
|---|---|---|---|---|---|---|
| 기존 19셀 | 1.0000 | **15.000** | **8** | **1** | **4.100** | **0.650** |
| derived-r6 | 2.4579 | 6.103 | 20 | 2 | 10.077 | 1.598 |
| daehan-79 | 3.8134 | 3.933 | 31 | 4 | 15.635 | 2.479 |

> **s (분산 보폭) 지수에 대한 주 — 유도와 실측이 갈린 곳.**
> 정교화의 중심 보정 예산은 `(0.34+0.12+0.04+0.012)·cellSize ≈ 0.51셀` 로 **발자국 반경과
> 무관**하다. 그러니 씨앗 격자 보폭도 반경 무관(s=0)이어야 한다는 것이 유도다.
> 실측은 s=0 이 «이동» 을 닫고 «복합» 을 열며 (7/8), s=1 이 그 반대 (7/8), s=0.25 가
> 둘 다 닫는다 (8/8). 유도는 s 를 «1보다 작다» 까지만 좁히고, 그 안에서 값을 고른 건
> 실측이다. 이 줄을 «유도했다» 고 쓰면 거짓이다.
>
> **`varianceCentersPerScale` 은 이 법칙 밖이다.** 현재 기본값이 0 (기능 꺼짐)이라
> 곱셈 법칙으로는 절대 켜지지 않는다. 실측이 말하는 것은 «ρ > 1 이면 켜야 한다» 이고,
> 몇 개인지는 8 과 16 이 각각 7/8 · 8/8 이다. 이건 **스위치 결정**이지 유도가 아니다.
> 그래서 순수 유도만 쓰는 지점(L2, 6/8, ×4.05)을 파레토에 남겨 뒀다.

읽는 법 — 브리프의 조건 «반경 10 때문에 반경 2 후보까지 비싸지면 안 된다» 는
**엄밀히 지켜진다**: 반경 2 만의 라인업은 10.41 → 11.04 ms 로 사실상 불변이고, 혼합

동시에 정직하게 적어야 할 것: **지금 daehan 을 라인업에 넣는 게 싼 이유(+1.02 ms,

### 3.2 검사 후보 4종

브리프 §4.2 의 예시(커버리지 · 바깥 잔차 · 스케일 정합)를 그대로 쓰지 말라고 해서,
그 중 하나(바깥 잔차)를 살리고 셋을 새로 설계해 **넷을 겨루게** 했다.

**A. 격자 이동 여유 `latticeMargin`** — 기존 `orientationMargin` 과 **같은 종류의 자**다
(그건 120°/240° 회전 대비 여유). 다른 것은 축이다: 회전이 아니라 **평행이동**.
발자국을 axial 이웃 6방향으로 한 칸씩 밀어 상관을 재고 `corr(H) − max(shifted)` 를 본다.
논거: 진짜 파인더는 한 칸만 밀어도 데이터 셀 위로 나가 상관이 무너진다. 구조화된 장의
아무 자리에 붙은 것은 한 칸 옆도 «비슷한 것» 이라 여유가 안 난다.

**B. 바깥 잔차 `outerStructure`** — 브리프 §4.2 의 «있어야 할 것이 없는가» 를 그대로
구현. 발자국 밖 고리(hex 거리 R+1 \~ R+2)의 표본에서 `(p90−p10)/span`. 크면 «내 발자국
밖에도 뭔가 많다» = 부분영역 혐의.

**C. 발자국 우세 재도전 `dominanceGap`** — 이긴 자세에서 **더 큰 발자국** 후보를 다시
정교화해, 그쪽이 더 잘 맞으면 내가 부분영역이었다는 뜻.
`corr(나) − max(더 큰 발자국들이 이 자세에서 도달한 corr)`. 브리프의 «커버리지» 와
«스케일 정합» 이 노리던 것(«큰 게 있는데 왜 작은 걸 골랐나»)을 직접 겨눈다.

**D. 배율 이동 여유 `scaleLock`** — A 의 배율판. `corr(H) − max(corr(H·S(0.85)), corr(H·S(1.18)))`.
브리프의 «스케일 정합» 을 이미지 추정 없이 **봉우리 날카로움**으로 바꾼 것.

### 3.3 4종 겨루기 (실측)

기준: **오수용 8건 중 몇 건을 잡는가** · **정상 검출을 몇 건 죽이는가** · **비용**.
«정상 검출» 은 두 층으로 나눴다 — `corr ≥ 0.99` 인 **본 검출 315건** (죽으면 진짜 손해)과
`corr < 0.99` 인 **약한 검출 217건** (이미 간신히 잡힌 것).
문턱은 「본 검출 0 사망」 지점에서 최대 검거로 잡았다.

| 검사 | 문턱 | 오수용 검거 | 본 검출 사망 | 약한 검출 사망 | 비용 (검출 대비) |
|---|---|---|---|---|---|
| **A `latticeMargin`** | ≥ 0.3444 | **8/8** | **0/315** | 20/217 | **0.128 ms (1.1%)** |
| B `outerStructure` | ≤ 0.9205 | 6/8 | 0/315 | 8/217 | 0.054 ms (0.5%) |
| C `dominanceGap` | ≥ 0.4693 | 8/8 | 0/221 | **61/153** | **5.035 ms (42.4%)** |
| D `scaleLock` | ≥ 0.1152 | 7/8 | 0/315 | 48/217 | 0.076 ms (0.6%) |
| A′ `min(lattice, orient)` | ≥ 0.2835 | 8/8 | 0/315 | 15/217 | 0.128 ms (1.1%) |
| **A″ `lattice/(1−corr)`** | ≥ 0.9774 | **8/8** | **0/315** | **13/217** | **0.128 ms (1.1%)** |

읽는 법:

- **C 는 값이 비싸고(검출의 42%) 위양성이 크다** (적용 가능한 153건 중 61건 사망 = 40%).
  이유는 §3.1 의 정정 그대로다 — 같은 크기끼리의 오수용에는 «더 큰 발자국» 이 daehan
  하나뿐이라 자가 엉뚱한 것을 잰다. **브리프가 지목한 방향이 실측에서 가장 나쁜 검사다.**
- **B 는 싸지만 8건 중 6건만** 잡고, 방향도 위험하다. 합성(파인더만) 프레임에서
  정상 검출의 중앙값이 0.000 인데 렌더 프레임에서는 데이터 셀 때문에 p75 가 0.709 다 —
  **프레임 종류에 따라 자가 통째로 다른 값을 낸다.** 실사진에서 어디로 갈지 모른다.
- **D 는 싸지만 7/8** 이고 위양성이 A 의 2.4배.
- **A 가 이긴다.** 그리고 A 의 최적 문턱을 정규화하면(A″) 더 좋아진다.

### 3.4 권고 — 어디에, 어떤 문턱으로

**`latticeMargin` 을 `finishCandidate` 의 하드체크에 네 번째로 더한다.**
게이트 3개는 한 값도 안 건드린다. 문턱은 상수가 아니라 **잔차 비례**로:

```js
// 격자 한 칸 이동 여유 — 기존 orientationMargin 의 평행이동판.
// (orientationMargin 이 120°/240° 회전에 대해 하는 일을 axial 이웃 6방향에 대해 한다)
const latticeMargin = best.correlation - Math.max(...AXIAL_STEP_XY.map((step) =>
  scoreAll(luma, multiply3(final.H, translationH(step.x, step.y)),
    [best.template], span, true)[0]?.correlation ?? -1));

hardChecks.lattice = latticeMargin >= LATTICE_KAPPA * (1 - best.correlation);   // κ = 1.0
```

**문턱 유도 — 왜 상수가 아니라 `1 − correlation` 인가.**
A 의 최적 절대 문턱은 0.3444 이고, 정규화판 `latticeMargin/(1−correlation)` 의 최적
문턱은 **0.9774 ≈ 1** 로 떨어진다. 1 에 붙는 것은 우연이 아니라 읽을 수 있는 문장이다:

> **«격자 이동 여유는 설명되지 않은 잔차보다 커야 한다.»**

상관 0.999 면 요구가 0.001 로 사실상 없고 (본 검출은 절대 안 죽는다), 상관 0.60 이면
0.40 을 요구한다 (오수용은 전부 여기 있다). **자가 스스로 조인다.**

κ 별 실측 분포:

| κ | 오수용 검거 | 본 검출(≥0.99) 사망 | 약한 검출(<0.99) 사망 |
|---|---|---|---|
| 0.50 | 1/8 | 0/315 | 2/217 |
| 0.75 | 5/8 | 0/315 | 7/217 |
| **1.00** | **8/8** | **0/315** | **15/217** |
| 1.25 | 8/8 | 0/315 | 28/217 |
| 1.50 | 8/8 | 0/315 | 39/217 |
| 2.00 | 8/8 | 0/315 | 67/217 |

κ=1.0 이 «전건 검거» 의 **최소** 지점이다 (0.75 로 낮추면 3건을 놓친다). 그 위로 올리면
검거는 안 늘고 약한 검출만 죽는다. **κ = 1.0 을 권고한다.**

κ=1.0 에서 죽는 정상 검출 15건은 전부 `corr 0.5729 \~ 0.6621` · 자세는 **이동 또는 복합**
뿐이다 (`gap-ring-01-2-1-solid/open` 6건, `pinwheel-3-0101` 4건, `flower-7-*` 3건,
나머지 2건). 즉 **«간신히 잡힌 것» 만 죽고 «제대로 잡힌 것» 은 하나도 안 죽는다.**
전건 목록은 `claude-rt-case2-gate.json` 의 `kappaOneDeaths`.

**브리프 §4.4 — 기존 14후보 정상 검출 전수 확인:**
14 × 8 렌더워프 112칸에서 `통과(≥0.99)` **44 → 44 (불변)**. 약한 검출(<0.99)이
37 → 35 로 2건 줄었다 (둘 다 이동/복합 자세, corr 0.57·0.62). **본 검출은 0 사망.**

**실제로 걸었을 때 무슨 일이 나는가** (`claude-rt-case2-gate.mjs` §5) —
오수용 8건 전부 **«조용히 틀린 답» → «검출 실패»** 로 전환된다 (구제 0 · 실패 전환 8 ·
미해결 0). 정답이 2순위로 올라오지는 않는다. 그건 검사가 아니라 탐색이 할 일이고,
탐색을 고치는 것이 건①이다 — 실제로 건① 을 같이 걸면 daehan 두 건은 애초에 1순위가
정답이 된다 (§4).

## 4. 두 건의 상호작용 (브리프 §5)

브리프의 가설: «①이 refined 를 늘리면 ②의 오수용이 늘어난다.» **부분적으로만 맞다.**

같은 프레임 집합(렌더워프 112 + daehan 8 = 120)에서 네 구성을 나란히 재면
(`claude-rt-integration.mjs`):

| | ⓐ 현재 소스 | ⓑ 반경법칙만 | ⓒ 격자검사만 | ⓓ 둘 다 |
|---|---|---|---|---|
| daehan 8자세 통과 | 3/8 | **8/8** | 3/8 | **8/8** |
| 기존 14 통과 (≥0.99, 112칸) | 44 | 44 | 44 | **44** |
| 기존 14 약한 검출 | 37 | 37 | 35 | 35 |
| 기존 14 오수용 | 1 | **2** | 0 | **0** |
| daehan 오수용 | 2 | 0 | 0 | **0** |
| **오수용 총계** | **3** | **2** | **0** | **0** |

- **①이 오수용을 늘리는 것은 사실이다 — 반경 2 쪽에서.** 반경법칙은 daehan 쪽 오수용
  2건을 **없애지만**(제대로 찾으니까), 반경 2 쪽에 **새 오수용 1건을 만든다**
  (`flower-7-0020 / 이동` → `pinwheel-3-0101`). 정교화 후보가 늘면 «게이트를 통과하는
  그럴듯한 오답» 이 더 많이 완성되기 때문이다. 순증감은 3 → 2 로 줄지만,
  **«늘어난다» 는 방향 자체는 브리프가 맞았다.**
- **②는 ①이 만든 것까지 포함해 전부 잡는다.** ⓓ 에서 오수용 **0**.
- **②가 ①을 방해하지 않는다.** ⓓ 의 daehan 통과수는 ⓑ 와 같은 8/8 이고 값도 동일하다
  (격자 검사가 정답 후보를 하나도 안 건드린다 — 정답은 전부 corr ≥ 0.99 라 요구가
  0.01 이하로 내려간다).
- **②만 걸면 ①의 문제는 하나도 안 풀린다** (ⓒ 3/8). 오답이 침묵으로 바뀔 뿐이다.
  ⓒ 열에서 daehan +7°/+37° 가 `★0.6403` → `F` 로 바뀌는 것이 그 그림이다.

비용:

| 구성 | 반경 2 프레임 (렌더) | daehan 프레임 (합성) |
|---|---|---|
| ⓐ 현재 소스 | 20.93 ms (×1.00) | 41.41 ms (×1.00) |
| ⓑ 반경법칙만 | 192.02 ms (×9.18) | 437.58 ms (×10.57) |
| ⓒ 격자검사만 | 18.61 ms (**×0.89**) | 34.85 ms (**×0.84**) |
| ⓓ 둘 다 | 226.30 ms (×10.81) | 572.16 ms (×13.82) |

**격자 검사는 공짜보다 싸다** (×0.89) — 후보 하나당 0.128 ms 를 쓰지만 걸린 후보가
NMS·후속 단계에서 빠지므로 상쇄된다. 비용은 전부 건① 쪽이다.

**결론: 두 권고는 충돌하지 않는다. 오히려 ②는 ①이 새로 만드는 위험의 정확한 상쇄다.**
①만 넣고 ②를 안 넣으면 반경 2 쪽 오수용이 늘어난 채로 배포된다.

## 5. 못 푼 것과 그 이유

1. **실사진이 없다.** 합성 프레임은 톤이 정확하고 잡음이 없고, 렌더 워프는 보간 흐림만
   있고 카메라 응답·조명 기울기·모아레가 없다. κ=1.0 이 실사진에서 본 검출을 0 죽인다는
   보장은 여기서 안 나온다 — **실사진 덤프가 생기면 §3.4 의 κ 표를 다시 그려야 한다.**
   특히 실사진은 정상 검출의 correlation 분포를 아래로 끌어내리므로 κ 요구가 커진다.
2. **원근/기울기(skew)를 안 흔들었다.** 8자세는 회전·배율·평행이동뿐이다. `latticeMargin`
   은 아핀 이웃 이동으로 정의돼 있어 강한 원근에서 어떻게 되는지 안 쟀다.
3. **반경 6 후보가 정본이 아니다.** `derived-daehan-r6` 는 daehan 의 hex 거리 ≤ 6 부분집합
   으로 **내가 만든** 자다. 비용 곡선의 중간점을 찍는 용도이고, «반경 6 후보의 검출력» 을
   말하지 않는다.
4. **`varianceCentersPerScale` 을 유도하지 못했다.** §2.4 주 참조 — 현재 기본값 0 은
   곱셈 법칙으로 켤 수 없다. 스위치 결정이 남아 있다.
5. **계단(cascade) 편성을 권고까지 못 밀었다.** 실기기에서 반경 10 코드의 비중을 모른다.
   반경 2 프레임 17.4 ms · 반경 10 프레임 524.1 ms 라는 실측만 남긴다.
6. **혼합 라인업의 «전 출력 비트 동일» 은 아니다.** `cats-refined-h3` 에서 2순위 후보가
   하나 더 생긴다 (최상위는 비트 동일). 소비자가 `candidates[1]` 을 보는 곳이 있다면
   확인이 필요하다.
7. **게이트를 내리자는 제안은 하지 않는다.** 위 어느 항목도 게이트 3개와 무관하다.
   건②는 게이트를 **더하는** 것이고, 건①은 게이트를 안 지난다.

## 6. 내가 틀렸다가 고친 것

브리프 §6.6 이 요구한 항목이다. 직전 라운드의 `j = i++` → `j = i += 1` 함정에 해당하는
것들 — 이번에는 **자를 잘못 쓴 이력** 쪽이 많았다.

1. **«구제됐다» 를 잘못 읽었다 — 두 변경을 한 실행에 섞었다.**
   격자 검사를 실제로 걸어 보는 §5 를 처음엔 `detectCellFindersRadius(radiusLaw: null)`
   로 돌렸다. 결과가 «daehan +7° 오수용 → 구제, 정답이 올라옴» 으로 나와서 그대로 쓸
   뻔했다. 그런데 `radiusLaw: null` 이어도 그 함수는 **조대 목록을 발자국별로 쪼갠다** —
   원본은 공유한다. 즉 «검사가 고쳤다» 가 아니라 **«그룹 분리가 고쳤다»** 였다.
   → `sharedCoarse` 옵션을 만들어 원본 흐름을 그대로 재현하게 하고, 렌더 14 + daehan
   +7° 에서 원본과 **비트 동일**임을 확인한 뒤 다시 쟀다. 답이 뒤집혔다:
   **구제 2 → 0, 실패 전환 3 → 8.** 「A 를 켜고 B 도 켠 채로 A 의 효과를 말하지 마라」.
2. **비용을 순차로 재다가 6.5배짜리 유령을 만들었다.**
   계단 측정에서 daehan 행이 «계단 1260.7 ms / 일괄 609.9 ms» 로 나왔다. 계단은
   1단계 + 2단계인데 2단계 혼자가 610 이면 1단계가 650 ms 라는 뜻이다. 이상해서
   1단계만 따로 재보니 **5.52 ms**. 순차 측정이라 드리프트가 뒤쪽 행에만 실린 것이다.
   → 라운드로빈(그리고 홀짝으로 순서 반전)으로 바꾸니 계단 = 1단계 + 2단계로 맞아떨어졌다.
   **「배수가 설명 안 되면 알고리즘이 아니라 자를 의심한다.」**
3. **창과 보폭을 한 지수로 묶었다 — 기하가 다른 두 조건인데.**
   첫 법칙은 `varianceWindowRadiusCells` 와 `varianceStepCells` 를 같은 ρ^w 로 키웠다.
   그랬더니 «이동» 자세가 어떤 지수 조합에서도 **0.7692 에 고착**했다. 값이 여러 조건에서
   똑같으면 그 축과 무관하게 결정됐다는 신호다 (직전 라운드의 교훈 그대로).
   파고 보니 창은 «분산 봉우리가 발자국 중심에 서게» 하는 조건(→ ρ 비례)이고,
   보폭은 «씨앗이 정교화의 중심 보정 예산 0.51셀 안에 들어오게» 하는 조건(→ 반경 무관)
   이었다. **한 지수로 묶으면 큰 발자국에서 씨앗 격자가 성글어져 이동을 영영 못 잡는다.**
   → 지수를 분리하자 0.7692 → **1.0000**.
4. **직전 라운드 보고서의 `√3·R` 를 그대로 쓸 뻔했다.**
   그 계수는 hex 거리 R 인 셀 중 «가장 먼 것» 을 가정한 값인데, daehan 의 반경 10 셀들은
   육각 모서리 방향에 몰려 있어 실제로는 **1.539·R** 이다 (12% 과대). R 의 함수로 쓰면
   반경 2 에서 상수 재현이 어긋난다.
   → 발자국의 표본점에서 **직접 재는** `reach` 로 바꿨다. 그래서 «반경 2 에서 현재 값이
   그대로 나온다» 가 근사가 아니라 `===` 가 됐다. 「인용한 상수도 재본다.」
5. **파레토 앞면을 ms 로 계산했다.**
   비용 배수는 기준선과 교대해 재서 드리프트에 강한데, 절대 ms 는 아니다. 앞면을
   ms 로 뽑으니 «7/8 최저비용» 이 L9(×10.04)로 나왔고, 배수로 뽑으면 L27(×8.03) 이다.
   → 보고서 표는 **배수 기준**으로 다시 뽑았다. 스크립트 출력의 앞면 줄은 ms 기준이
   남아 있으니 (`claude-rt-case1-law.json`), 둘이 다를 때는 배수가 맞다.
6. **브리프의 전제 하나를 반증했다 (§3.1).**
   브리프는 오수용을 «큰 발자국 안에 작은 템플릿» 으로 규정하고 그 축으로 재라고 했다.
   실측은 8건 중 **6건이 같은 크기끼리**다. 브리프가 «안 날 것 같지만 재라» 고 못 박아
   둔 덕에 잡혔다 — 안 쟀으면 «큰 발자국 재도전»(검사 C)을 권고할 뻔했고, 그건 실측에서
   **가장 비싸고 가장 위양성이 큰** 검사였다. **가설이 처방을 좁히는 방식이 위험하다.**
