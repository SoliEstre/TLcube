## 1. 결론 한 줄

**못 찾았다 — 브리프가 건 제약(소스 불변) 안에서는 어떤 `calibration` 조합도

## 2. 원인 — `refine()` 이 발자국을 못 받는다

`src/decoder/cell-finder-detect.js:462`

```js
function scoreParams(luma, params, template, span) {
  const H = HFrom(params);
  const sampled = observationsAt(luma, H, true);   // ← 발자국 인자가 없다
  ...
  const scored = scoreTemplate(sampled, template, span);
```

`observationsAt(luma, H, detailed, faceSamples = FACE_SAMPLES)` 의 넷째 인자가
비어 있어 **언제나 기본 19셀 표본**을 뜬다. 2026-08-18 발자국 파라미터화는
`buildFaceSamples` · `faceSamplesFor` · `footprintOf` · `groupByFootprint` ·
`scoreAll` · `scoreBest` 까지 배선됐는데 **이 한 곳만 빠졌다.**

결과로 daehan-79 를 정교화할 때:

- 관측: 기본 19셀에서 뜬 228 값 (19 × 3면 × 4점)
- 기대: daehan-79 템플릿 948 값 (79 × 3면 × 4점)
- `scoreTemplate` 은 `sampled.values.length`(228)까지만 돌므로 **템플릿 앞 228 값만** 쓰인다
  = 발자국 배열의 **앞 19셀만** 본다. 길이 불일치가 조용히 잘린다.

그래서:

- 앞 19셀이 `FINDER_CELL_ORDER` 와 같으면 (center-first) 기하가 우연히 맞아 «반경 2 정합» 으로 퇴화 → 씨앗이 정확할 때만 수렴
- 앞 19셀이 다르면 (canonical) **A 셀의 관측을 B 셀의 기대와** 맞추게 됨 → 0.6058 에 고착
- 정교화의 목적함수가 반경 2 밖을 **못 보므로**, 스케일·각도·후보 수를 아무리 흔들어도 그 값이 안 움직인다 (§3 에서 실측)

## 6. 한계 — 무엇을 바꿔야 하는가 (브리프 §7.6)

### 6.1 소스 불변 조건에서는 어느 축도 안 듣는다

§3 대로 7축 전부 `0.6058` 에 고착이다. 이유는 §2 — 정교화의 **목적함수가
반경 2 밖을 못 본다**. 손잡이는 씨앗(어디서·어느 배율로·몇 개나 시작하나)을
바꾸지만, 목적함수가 먼 셀에 눈이 없으면 어디서 시작해도 같은 곳에 선다.
**따라서 이건 파라미터 문제가 아니라 구조 문제다.**

### 6.2 순서를 바꿔 «고치는» 것은 함정이다

### 6.4 권고 (구현은 이 레인의 범위 밖)

1. **`scoreParams` 의 발자국 인자를 채운다** — 한 줄, 기존 14후보 비트 동일, 비용 ×1.06.
   이게 선결이다. 이걸 안 하면 아래 2·3은 전부 헛일이다.
2. **`coarseAngleStepDegrees` 와 `varianceWindowRadiusCells` 를 발자국 반경의 함수로
   만든다** (고정 상수 폐기). 반경 2 에서는 지금 값이 그대로 나오도록 잡으면
   기존 14후보에 영향이 없다.
3. **길이 불일치를 조용히 삼키지 않게 한다** — `scoreTemplate` 이
   `sampled.values.length !== expected.length` 일 때 throw 하면 이 결함은
   애초에 24시간을 먹지 않았다. 회귀 테스트보다 이 단언이 싸다.
4. **오수용 게이트를 따로 본다** (§4 소견) — 발자국 크기가 크게 다른 후보가
   같은 라인업에서 겨룰 때 NCC 만으로는 «부분 일치» 를 못 거른다. 게이트를
   내리자는 게 아니라 **차원이 다른 검사가 하나 더 필요하다**는 뜻이다.

**게이트를 내리자는 제안은 하지 않는다.** 위 어느 항목도 게이트와 무관하다.

### 6.5 이 측정이 말하지 않는 것

- 합성 프레임이다. 톤이 정확하고 잡음이 없고 데이터 셀이 없다. 실물에서
  «되는가» 는 여기서 안 나온다 — 재는 건 «표현·탐색 경로가 성립하는가» 뿐이다.
- 자세 8개는 회전·배율·평행이동뿐이다. 원근/기울기(skew) 는 안 흔들었다.
- 8/8 은 **패치 사본**의 성적이다. 정본 소스의 성적이 아니다.

## 7. 내가 틀렸다가 고친 것 (브리프 §7.7)

1. **점-다각형 판정을 «정리» 하다 깨뜨렸다.**
   원문 `j = i++` 를 `j = i += 1` 로 옮겨 적었다. 전자는 j 에 **옛** i 를,
   후자는 **새** i 를 준다. 변이 하나도 안 닫혀 합성 프레임이 통째로 틀렸고,
   참 자세 대조군이 **0.5136** 으로 나왔다. 브리프 §5 가 «대조군이 1.0 이 아니면
   네 합성이 틀린 것» 이라고 못 박아 둔 덕에 스윕을 한 번도 안 돌리고 잡혔다.
   → 대조군은 장식이 아니다. 갱신식은 `j = i, i += 1` 이 맞고, 사본에 주석으로 박아 뒀다.

2. **패치 사본에서 상수까지 개명해 죽였다.**
   이름 충돌을 피하려고 `UNVERIFIED_CELL_FINDER_CALIBRATION` 을 개명했는데
   모듈 내부 `cfgFor` 가 그 이름을 참조해 `ReferenceError`. 함수 export 만 개명해야 한다.

3. **`scaleRatio` 가 «안 듣는다» 고 적을 뻔했다.**
   `cellSizeSeeds` 를 주면 `scaleSeeds()` 가 그 값을 **읽지도 않는다**.
   «듣지 않는다» 와 «전달되지 않는다» 는 다른 결론이고, 후자를 전자로 적으면
   다음 사람이 그 축을 영영 안 본다. 두 조건 모두 재서 표에 나눠 적었다.

4. **브리프 §2 의 전제를 반증했다.**
   브리프는 «탐색이 참 자세로 수렴하지 못한다 → 남은 손잡이는 스케일·각도·후보 수»
   라고 썼다. 앞 절은 맞지만 뒤 절이 틀렸다. 손잡이가 안 듣는 이유는 손잡이가
   모자라서가 아니라 **정교화가 보는 대상 자체가 틀려서**다. 손잡이만 계속
   돌렸으면 «전수 스윕했는데 안 된다» 로 끝났을 것이다.
   → 값이 **여러 조건에서 소수 4자리까지 똑같으면** 그건 잡음이 아니라
   «그 값이 그 축과 무관하게 결정됐다» 는 신호다. 통합자가 이미 «4가지 조합에서
   안정적» 이라고 적어 뒀는데, 그게 결정 단계를 가리키는 화살표였다.

5. **재현 실패를 «내 잘못» 으로만 보지 않았다.**
   §8 ②가 «0.6058 이 안 나온다» 로 떨어졌을 때 합성을 의심하는 게 기본이지만,
   대조군이 이미 1.0 이었으므로 합성은 맞았다. 남은 차이는 «내가 자유롭게 정한 것»
   = 발자국 순서뿐이었고, 그것만 바꿔 재서 0.6058 을 정확히 재현했다.
   → 재현이 안 되면 **내가 임의로 정한 것 목록**부터 훑는다.
