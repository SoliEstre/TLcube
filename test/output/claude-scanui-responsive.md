## 1. 현황 진단 — 어디서 페이지 스크롤이 나는가

### 1.1 구조적 원인 (수치 이전의 이유)

`sites/tlscan/index.html` 변경 전 상태:

```
.scanner-app   { min-height: 100dvh; overflow: hidden; }
.scanner-shell { display:flex; flex-direction:column; gap:10px;
                 min-height: 100dvh; padding: max(10px, safe-inset); }
.square-stage-wrap { flex: 1 1 auto; min-height: 0; place-items:center; }
.square-stage      { width: min(92vw, 92dvh); aspect-ratio: 1/1; }
html, body         { min-height: 100%; }   /* 높이 상한 없음 */
```

핵심은 **`min-height` 는 상한이 아니라는 것**이다.

1. 셸이 `height:auto + min-height:100dvh` 라서, 자식 높이 합이 100dvh 를 넘으면
   셸의 사용 높이는 **콘텐츠 높이**가 된다.
2. 그러면 flex 컨테이너의 free space 가 0 이므로 `flex-shrink` 가 **발동하지 않는다**.
   `.square-stage-wrap { flex: 1 1 auto; min-height: 0 }` 는 «줄어들 수 있게» 보이지만
   줄어들 계기가 영영 오지 않는다.
3. `.scanner-app { overflow: hidden }` 도 막지 못한다 — app 박스 자신이 in-flow 자식을
   따라 커지기 때문에 잘라낼 초과분이 없다. 결국 body 가 뷰포트보다 길어져
   **페이지가 스크롤된다**.

즉 «정사각 92% + 아래 스택» 은 스택 높이를 전혀 고려하지 않는 배치였고, 8 dvh 의 잔여
공간이 스택을 담을 수 있다는 **암묵 가정**만 있었다.

### 1.2 요소별 높이 (CSS 선언에서 유도)

브라우저 실측이 아니라 CSS 선언값 산술이다 (실측은 통합자 몫). 근거는 각 행의 산식.
`line-height: normal` 은 1.2 로 잡았다.

| `.scanner-top` (`.brand-logo`) | padding 8+8 + border 1+1 + font 14px × lh 1 | **32.0** |
| ↳ `.lang-switch` | 버튼 5+5+12×1.2 = 24.4, + padding 2+2 + border 1+1 | 30.4 (작은 쪽) |
| `.scan-guide-message` | padding 8+8 + L × (clamp(14,3.8vw,16) × 1.35) | 16 + L·lh |
| `.scan-scope-note` | margin −8 + padding 5+5 + border 1+1 + L × (12 × 1.35) | 4 + L·16.2 |
| `.scan-guide-wrap` | grid gap 8 × 2 | +16.0 |
| `.scan-status` | padding 7+7 + L × (13 × 1.4) | 14 + L·18.2 |
| `.zoom-controls` | padding 8+8 + border 1+1 + 버튼 44 | **62.0** |
| `.photo-button` | min-height 52 (내용 47.2 보다 큼) | **52.0** |
| `.scanner-bottom` | padding-top 12 + grid gap 12 × 2 | +36.0 |

**모든 텍스트가 1줄일 때**(= 가능한 최소) 정사각 아래·위 UI 합:

```
UI_min(lh) = 32.0                       (top)
           + (16 + lh) + 20.2 + 20.2 + 16   (scan-center: 메시지 + 안내2 + gap)

           + 22.85                      (footer)
           + 40 + 20                    (shell gap ×4 + padding)
           = 369.45 + lh
```

| 폭 | `clamp(14px,3.8vw,16px)` | lh = ×1.35 | UI_min |
|---|---|---|---|
| 320 px | 14.00 | 18.90 | **388.35** |
| 344 px | 14.00 | 18.90 | **388.35** |
| 390 px | 14.82 | 20.01 | **389.46** |
| ≥ 421 px | 16.00 | 21.60 | **391.05** |

UI_min 은 폭이 변해도 **388–392 px 로 거의 상수**다. 이것이 진단의 핵심이다 —
정사각은 화면에 비례해 커지는데 UI 예산은 커지지 않는다.

### 1.3 스크롤 원인 진단표 (변경 전)

무스크롤 조건: `0.92·min(W,H) + UI_min ≤ H`.
아래 «초과» 는 **텍스트가 전부 1줄이라고 가정한 최선의 경우**의 초과분이다 —
줄바꿈이 생기면 더 나빠지기만 한다.

| 뷰포트 | 비율 W/H | 정사각 변 (0.92·min) | UI_min | 합계 | 뷰포트 H | 판정 |
|---|---|---|---|---|---|---|
| 390×844 (폰) | 0.462 | 358.80 | 389.46 | 748.26 | 844 | ✅ 여유 95.7 |
| 344×882 (폴드 접힘) | 0.390 | 316.48 | 388.35 | 704.83 | 882 | ✅ 여유 177.2 |
| 320×980 (극단 세로) | 0.327 | 294.40 | 388.35 | 682.75 | 980 | ✅ 여유 297.3 |
| **768×1024 (태블릿 세로)** | 0.750 | 706.56 | 391.05 | **1097.61** | 1024 | ❌ **초과 73.6** |
| **1024×768 (태블릿 가로)** | 1.333 | 706.56 | 391.05 | **1097.61** | 768 | ❌ **초과 329.6** |
| 1812×2176 (폴드 펼침, 브리프 표기) | 0.833 | 1667.04 | 391.05 | 2058.09 | 2176 | ✅ 여유 117.9 |
| **2176×1812 (폴드 펼침 가로)** | 1.201 | 1667.04 | 391.05 | **2058.09** | 1812 | ❌ **초과 246.1** |

가로 두 건이 왜 기존 가로 미디어쿼리에 안 걸렸나: 그 쿼리 조건이
`@media (max-height: 620px) and (orientation: landscape)` 였다. 1024×768 은 높이 768,
2176×1812 는 높이 1812 — **둘 다 620 을 넘어 세로 스택 그대로 렌더된다.** 즉 기존
가로 대응은 «높이가 낮은 폰 가로» 전용이었고 태블릿·폴드 가로는 사각지대였다.

### 1.4 «세로 길쭉한 경우도 비율에 따라» 의 정확한 경계

세로(W<H)에서 스크롤이 나는 조건을 정리하면

```
0.92·W + UI_min > H     ⟺     W/H  >  (1 − UI_min/H) / 0.92
```

UI_min ≈ 390 px 는 거의 상수이므로 **임계 비율은 H 에 따라 올라간다**:

| 세로 화면 높이 H | 임계 W/H | 뜻 |
|---|---|---|
| 640 | 0.424 | W > 271 이면 스크롤 |
| 844 | 0.583 | W > 492 이면 스크롤 |
| 1024 | 0.672 | W > 688 이면 스크롤 → **768×1024 위반** |
| 1180 | 0.729 | W > 860 이면 스크롤 |
| 2176 | 0.892 | W > 1941 (1812 는 통과) |

정리 — 진단 결론 두 줄:

- **세로에서도 안전한 것은 «가늘고 긴» 폰뿐**이다. 비율이 대략 **0.58 을 넘는 순간**
  (H=844 기준) 스택이 화면 밖으로 밀린다. 태블릿 세로(0.75)·폴드 펼침 CSS 세로가
  여기 걸린다.
- **가로는 높이 620 px 초과이면 전부 위반**이다 (기존 가로 쿼리가 안 걸리므로).

측정 못 한 것 (추측으로 메우지 않음):
- 브리프의 `1812×2176` 은 Galaxy Z Fold 계열의 **디바이스 픽셀**이다. DPR 2.625 를
  적용한 CSS 뷰포트는 대략 `690×829` 인데, 그 값이면 `0.92·690 + 391 = 1025.8 > 829`
  로 **초과 196.8 px** 이 된다. 어느 쪽이 실기기 값인지는 실측이 필요하므로 매트릭스에
  **둘 다** 넣었다 (브리프 표기 그대로 + CSS 환산 추정치).

### 1.5 진단의 실측 검증 (모델 → 사실)

브리프는 실측을 통합자 몫으로 뒀지만, «모델이 맞는가» 는 값싸게 확인할 수 있어서
확인했다. **변경 전 `index.html`(HEAD 원본)** 을 dev 서버로 띄우고 뷰포트를 바꿔가며
`documentElement.scrollHeight − clientHeight` 를 읽었다 (Chromium, 줌 컨트롤 + 렌즈
선택을 **노출 강제**한 최악 구성 — 실기기에서 다중 렌즈일 때의 상태).

| 뷰포트 | 정사각 변 (실측) | **페이지 세로 스크롤 (실측)** | 모델 예측 (1줄 가정) |
|---|---|---|---|
| 390×844 | 358.80 | **0** | 여유 95.7 → 통과 ✔ |
| 344×882 | 316.47 | **0** | 여유 177.2 → 통과 ✔ |
| 320×980 | 294.39 | **0** | 여유 297.3 → 통과 ✔ |
| 768×1024 | 706.55 | **128 px** | 초과 73.6 → 위반 ✔ |
| 1024×768 | 706.55 | **384 px** | 초과 329.6 → 위반 ✔ |
| 1812×2176 | 1667.03 | **0** | 여유 117.9 → 통과 ✔ |
| 2176×1812 | 1667.03 | **301 px** | 초과 246.1 → 위반 ✔ |
| 690×829 (폴드 CSS 환산) | 634.80 | **251 px** | 초과 221.8 → 위반 ✔ |
| 844×390 (폰 가로) | 358.80 | **68 px** | — |

- **어느 뷰포트가 스크롤되는지에 대한 모델의 판정은 9/9 일치**했다. 초과량이 모델보다
  큰 이유는 두 가지다: ① 렌즈 선택 `<select>` 가 +45 px ② `.scan-scope-note` 첫 줄이
  실제로 2줄로 접힌다 (390 px 폭에서 44.38 px = 12 + 2×16.19).
- 추가 발견 — **844×390 (폰 가로) 도 68 px 스크롤됐다.** 여기는 구 가로 미디어쿼리
  (`max-height:620px and landscape`) 가 **적용되는데도** 넘쳤다. 즉 구 가로 대응은
  «높이 620 초과를 못 잡는» 문제만이 아니라 «적용돼도 부족한» 문제도 있었다.
- 요소 높이 실측 (390 px 폭): 로고 32.00 · 메시지 35.98 · 안내1 44.38(2줄) ·
  안내2 28.19 · 상태 32.19 · 줌 62.00 · 사진 버튼 52.00 · 렌즈 선택 35.00 ·
  푸터 20.38. 1.2절 산식과 전부 ±0.2 px 이내로 일치했다 (푸터만 `<small>` 축소 때문에
  모델 22.85 → 실측 20.38 로 모델이 보수적).

## 2. 배치 설계 — 모드 · 경계 비율 · 산식

### 2.1 페이지 스크롤 0 을 «구조» 로 만든다 (1층)

```
html, body     { height: 100%; overflow: hidden; overscroll-behavior: none; }
.scanner-app   { height: 100dvh; overflow: hidden; }
.scanner-shell { height: 100dvh; overflow: hidden; }   ← min-height 아님
```

`min-height` → `height` 로 바꾼 것이 결함의 직접 수정이다. 이제 셸은 콘텐츠와
무관하게 정확히 뷰포트 높이이고, 문서가 뷰포트보다 커질 경로가 **없다**.

### 2.2 넘침을 흡수하는 지점을 하나로 (2층)

`.scan-center` + `.scanner-bottom` 을 새 래퍼 `.scanner-panels` 로 묶었다 (HTML 변경은
이 `<div>` 하나뿐).

```
.scanner-top, .site-footer { flex: 0 0 auto; }     /* 안 줄어든다 */
.square-stage-wrap         { flex: 1 0 auto; }     /* 남는 공간만 먹고, 안 줄어든다 */
.scanner-panels            { flex: 0 1 auto; min-height: 0; overflow-y: auto; }
.scanner-panels > *        { flex: 0 0 auto; }     /* 눌리는 대신 스크롤한다 */
```

`flex-shrink` 를 패널에만 남겨서, 넘칠 때 **줄어드는 곳이 한 군데뿐**이다. 그래서
배치가 결정적이다. 같은 이유로 `.lab-notice`(34 dvh 캡)와 `.camera-gate` 도 각자
`overflow-y: auto` 를 갖는다 — 페이지가 못 스크롤하니 잘리지 않으려면 자기 안에서
스크롤해야 한다.

⚠ `.scanner-panels` 에 `justify-content: center` 를 **쓰지 않았다**. column flex +
overflow 조합에서 넘칠 때 위쪽 초과분이 스크롤로 도달 불가해지는 동작 때문이다.

### 2.3 배치 모드 — 경계 비율

| 모드 | 조건 | CSS | 배치 |
|---|---|---|---|
| `stack` | W/H < 0.9 | 기본 (flex column) | 정사각 위 · 패널 아래 |
| `split` | W/H ≥ 0.9 | `@media (min-aspect-ratio: 9/10)` (grid) | 정사각 왼쪽 열 · 패널 오른쪽 열 |

- 경계 0.9 는 브리프 지정(«aspect ≥ 약 0.9»)을 그대로 썼다. `SPLIT_MIN_ASPECT = 0.9`
  ↔ `min-aspect-ratio: 9/10` 이 짝이고, 테스트가 유리수 변환까지 대조한다.
- **구 조건 `(max-height: 620px) and (orientation: landscape)` 는 폐기했다.** 높이가
  620 을 넘는 가로(태블릿·폴드)를 못 잡은 것이 위반의 원인이었다. 게이트 카드 여백만
  높이 조건으로 분리해 남겼다 (`@media (max-height: 620px)`) — 그건 비율이 아니라
  절대 높이의 문제라 조건이 다르다.
- split 의 grid 는 `grid-template-areas` 다. `[hidden]{display:none}` 인 lab 안내는
  그리드 아이템이 아니어서 자동 배치를 쓰면 행이 밀리기 때문이다.

### 2.4 정사각 뷰 한 변 — 산식

CSS 커스텀 속성과 `scanner-zoom.js scanLayout()` 이 **항의 순서까지** 같다.

```
availW = 100vw − padL − padR          pad* = max(10px, env(safe-area-inset-*))
availH = 100dvh − padT − padB
vminCap = min(92vw, 92dvh)                              ← squareViewSide() 와 같은 식

stack:  side = max(96px, min(vminCap, availW, availH − uiMinH))
        uiMinH = min(416px, 52dvh)

split:  side = max(96px, min(vminCap, availH, availW − uiMinW − 14px))
        uiMinW = min(300px, 42vw)
```

**UI 예산 416 px 의 분해** (CSS `calc()` 항과 문자 그대로 동일, 1.2절 산식에서 유도):

| 항 | px | 근거 |
|---|---|---|
| top | 36 | `.brand-logo` 32 + 여유 |
| guide | 132 | 메시지 2줄 59.2 + 안내1 2줄 36.4 + 안내2 1줄 20.2 + grid gap 16 |
| status | 34 | `.scan-status` 1줄 32.2 + 여유 |
| zoom | 62 | padding 16 + border 2 + 버튼 44 |
| photo | 52 | `.photo-button` min-height |
| footer | 24 | padding-top 8 + 11px×1.35 + 여유 |
| gaps | 76 | 셸 gap 10×3 + 패널 gap 10 + `.scanner-bottom` (padding 12 + gap 12×2) |
| **합** | **416** | |

즉 예산은 «안내가 전부 최대 줄 수로 접힌 폰» 을 담는 값이다. 실제 콘텐츠가 이보다
크면 패널이 내부 스크롤을 갖고, 작으면 정사각이 그만큼 커진다 — **어느 쪽도 페이지를
스크롤시키지 않는다**.

**두 개의 비율 캡** (`52dvh` · `42vw`) 을 둔 이유: 예산이 고정 px 이면 작은 화면에서
정사각이 하한까지 밀려 «카메라 뷰» 로서 기능을 잃는다. 캡은 «정사각이 가용 세로의
절반(가로의 58%) 아래로 내려가지 않는다» 를 뜻하고, 캡이 걸린 화면에서는 대신 패널이
내부 스크롤을 갖는다. 42 vw 캡은 고정 300 px 이었다면 생겼을 «가로 430 px 절벽»
(그 아래에서 예산이 성립하지 않는 구간) 도 없앤다.

**하한 96 px** 은 `width` 가 음수가 되어 선언 전체가 무효화되는 것을 막는 안전장치다.
걸리는 구간은 스택 세로 < 242 px / 옆배치 가로 < 225 px 로, `body{min-width:320px}`
인 이 앱에는 존재하지 않는다. 걸리면 `scanLayout().fits === false` 로 **드러난다** —
조용히 넘치지 않는다 (테스트가 그 경계를 고정).

## 4. `squareViewSide()` 동기화 처리

**함수는 유지하고 의미를 좁혔다.** `squareViewSide(w,h) = 0.92 × min(w,h)` 는 이제
새 산식의 **시각 여백 상한 항 하나**(CSS `--tl-vmin-cap`)를 담당한다. 새 정본은
`scanLayout()` 이고, 두 함수의 관계는 테스트가 단언한다:
`scanLayout(...).squareSide ≤ squareViewSide(w,h)` (전 뷰포트).

CSS 쪽도 `min(92vw, 92dvh)` 문자열을 그대로 보존했다 — 기존 가드
`assert.match(SCANNER_HTML, /min\(92vw, 92dvh\)/)` 는 **약화 없이 그대로 통과**하고,
`--tl-vmin-cap: min(92vw, 92dvh);` 를 짚는 단언을 하나 더 얹었다.

동기화 가드 확장 (`test/scanner-zoom.test.js`):

- CSS 커스텀 속성 **10 개**를 JS 상수에서 문자열로 **재구성해 대조**한다
  (`--tl-pad-{t,r,b,l}` · `--tl-shell-gap` · `--tl-split-gap` · `--tl-avail-{w,h}` ·
  `--tl-vmin-cap` · `--tl-ui-stack-h` · `--tl-ui-min-h` · `--tl-ui-min-w` ·
  `--tl-square-side` 2판). `@supports not (height: 1dvh)` 의 vh 폴백판까지 순서대로
  본다 — 값이 갈리면 즉시 실패한다.
- `--tl-ui-stack-h` 의 `calc()` 항은 `UI_STACK_BUDGET_PARTS` 의 **선언 순서·값 그대로**
  생성해 비교한다. 예산 한 항만 바꿔도 잡힌다.
- 미디어쿼리 `9/10` ↔ `SPLIT_MIN_ASPECT = 0.9` 유리수 대조.
- 구조 단언: `min-height: 100dvh` 잔존 금지(결함 그 자체), `.scanner-panels` 존재와
  `overflow-y: auto`, shrink 정책 3종, `100vw` 기준 `max-width` 3종 제거 확인.
- 회귀 증인: 구 산식 `squareViewSide + UI_STACK_BUDGET` 이 768×1024 · 1024×768 ·
  2176×1812 · 690×829 에서 **넘쳤음**을, 그리고 390×844 · 344×882 · 320×980 에서는
  **안 넘쳤음**을 같이 고정한다 (결함이 «세로 전부» 가 아니라 «비율» 이었다는 진단).

`renderGuideDots()` 는 손대지 않았다 — 스테이지의 `getBoundingClientRect()` 를 읽으므로
한 변이 어떻게 정해지든 그대로 성립한다. 프리뷰 ≡ 분석(`previewSourceWindow` ≡
`cropWindow`) 증명도 컨테이너 크기와 무관하므로 불변이다 (해당 테스트 통과 유지).

## 7. 무엇이 회귀였나 — «무스크롤» 과 «도달성» 은 다른 축이다

직전 적대 검증이 잡은 것: 짧은 폰(375×667 · 360×640)에서 평상 상태(줌 컨트롤 노출)에
**«사진에서 스캔» 버튼이 화면 밖**이다. 페이지는 여전히 스크롤 0 이다 — 잘림이 패널
**안**으로 옮겨졌을 뿐이고, r4 가 잰 자(콘텐츠 폭·높이 ≤ 뷰포트)에는 그 축이 없었다.

r4 의 §3 매트릭스가 초록이었던 이유는 두 가지다.

1. **표본에 그 구간이 없었다.** r4 뷰포트 9종의 세로는 전부 `h ≥ 844` 였다. 예산 캡
   (`52dvh`)이 실제로 걸리는 것은 `0.52h < 416`, 즉 **`h < 800`** 구간뿐이다. 캡이
   안 걸리면 패널은 예산 416 을 통째로 받으므로 아무것도 안 밀린다.
2. **재는 축이 하나였다.** 「콘텐츠 ≤ 뷰포트」 는 페이지의 성질이고, 「무엇이 먼저
   밀리나」 는 패널 **안**의 성질이다. 후자는 산식이 아니라 **DOM 순서**가 정한다.

## 8. 수정 1 — 패널 내 우선순위 재배열

`.scanner-panels` 안의 **DOM 순서**를 바꿨다.

```
r4:  안내 문구 → [상태 · 줌 · 사진 버튼 · 렌즈 선택]
r5:  [상태 · 줌 · 사진 버튼] → 안내 문구 → 렌즈 선택 · 파일 입력
```

- 구현은 «`.scanner-bottom` 을 `.scan-center` 앞으로» + «렌즈 선택·파일 입력을
  `.scanner-bottom` 밖으로 빼 맨 뒤로». 새 래퍼를 안 만든 이유: 빈 래퍼도 flex gap
  10 px 를 **무조건** 먹는데, 렌즈 선택은 다중 렌즈 기기에서만 나타난다. 직계 자식으로
  두면 `hidden`(display:none) 일 때 gap 자체가 생기지 않는다.
- `.camera-picker` 에 `align-self: center` 를 더했다 — 구조상 grid 아이템
  (`justify-items: center`)에서 열 flex 자식으로 바뀌어 기본 stretch 로 왼쪽에 붙는다.
  실측 확인: 패널 중심과의 편차 **0.00 px**.
- **CSS `order` 를 쓰지 않았다.** order 는 시각 순서만 바꾸고 초점·낭독 순서는 DOM 을
  따라가 둘이 갈린다. 테스트가 `order` 선언 잔존을 금지한다.
- i18n 속성·기존 id 전부 보존 (`data-i18n="button.photo"` · `status.preparing` ·
  `aria-label:picker.label` 을 이동 후 위치에서 다시 단언). **신규 문구 0** —
  `scanner-i18n.test.js` · `i18n-coverage.test.js` 통과 유지.

⚠ 낭독 순서가 «컨트롤 → 안내» 로 바뀌었다. 상태줄이 `role=status aria-live` 로 먼저
읽히고 안내는 그 뒤에 온다 — 시각 순서와 갈리지 않는다는 점이 이 선택의 근거다.

## 9. 수정 2 — 스크롤 힌트 (내부 오버플로일 때만)

잘리는 쪽이 «설명» 으로 옮겨졌어도 **잘렸다는 사실**은 보여야 한다. 안 그러면 안내가
애초에 없는 화면으로 읽힌다.

**순수 CSS 로 못 한 이유** (브리프가 요구한 판단):

- 흔히 쓰는 `background-attachment: local` 스크롤 그림자 기법은 **불투명한 덮개
  레이어**로 그림자를 가리는 방식이다. 이 패널의 배경은 투명이고 뒤가 카메라 화면이라
  덮개를 만들 수 없다.
- `animation-timeline: scroll()` 은 iOS Safari 에 없다 — 정작 대상 기기가 사각지대다.

그래서 **판정만 JS**(`scanner.js syncPanelScrollHint`), **그리는 것은 CSS 마스크**로
갈랐다. 전송 0 바이트(외부 자원 없음), 레이아웃 무변경, 클래스 하나만 토글한다.

```
판정: scrollTop + clientHeight < scrollHeight − 1     ← «아래에 더 있나»
그림: .scanner-panels.has-more { mask-image: linear-gradient(to bottom,
        #000 calc(100% - 28px), transparent) }        ← -webkit- 접두사판 동반
```

판정을 «오버플로» 가 아니라 «아래에 더 있나» 로 둔 것은 의도적이다. 스크롤 위치가 맨
위인 평상 상태에서는 두 조건이 같고(`scrollHeight > clientHeight`), 끝까지 내리면
저절로 꺼진다 — 끝에서 남는 페이드는 «아직 더 있다» 는 거짓말이 된다.

재평가 트리거는 스크롤·리사이즈·회전 + **자식까지 관찰하는 `ResizeObserver`** 다.
패널 자신만 보면 부족하다: 이미 넘친 패널은 콘텐츠가 늘어도 `clientHeight` 가 안 바뀌고
`scrollHeight` 만 늘어서 관찰자가 안 깨어난다 (줌 컨트롤 노출·렌즈 선택 등장·상태 문구
줄바꿈이 전부 이 경로다). `ResizeObserver` 미지원 환경은 `typeof` 로 건너뛴다.

## 10. 수정 3 — 부수 정정 2건

**(a) `scanner-zoom.js` JSDoc 의 400 px** — `UI_BUDGET_CAP_FRACTION` 과 `scanLayout()`
주석이 근거를 400 으로 적고 있었는데 실제 상수는 **416** 이다. 예시 수치도 따라 틀려
있었다(세로 568 화면에서 «정사각 148px» → 실제 **132px** = 568 − 20 − 416). 산식은
처음부터 416 을 썼으므로 **코드 동작은 무변경** — 틀린 것은 서술뿐이었다.

**(b) `claude-square-view-matrix.json` 의 `squareSide`** — r3 매트릭스 테스트가 구 산식
(0.92 × 짧은 변) 값을 «뷰 변» 이라는 이름으로 공표하고 있었다. r4 부터 실제 한 변은
여기에 배치 적합 상한을 더 min 한 값이라, 예컨대 태블릿 1024×768 의 실제 변은 **690**
인데 이 표는 **706.56** 을 싣고 있었다.

- 필드명 `squareSide` → **`viewSideCap`**, 테스트 제목·주석을 «시각 여백 상한» 으로 정정
  (r4 의 `squareViewSide()` 의미 축소와 같은 정정).
- JSON 에 `viewSideCapMeaning` 한 줄을 넣어 **산출물이 스스로를 설명**하게 했다.
- 이름이 뜻하는 관계를 단언으로 고정: `scanLayout().squareSide ≤ viewSideCap` (전 뷰포트).
- 같은 수치를 표로 공표하던 `claude-overlay-guide3.md` §6 도 정정했다 (상한 열 + 실제 뷰
  변 열로 분리, 정정 사유 인용문 첨부). 공표된 곳을 안 고치면 정정이 반쪽이다.

## 11. 수정 4 — 매트릭스 표본 확장 + 신규 단언

`R4_VIEWPORTS` 에 `375×667` · `360×640` 추가 (총 11종). 둘 다 스택이고 `binding: fit`,
`uiBudget < 416`(캡이 실제로 걸림)임을 단언으로 못박았다 — 표본이 그 구간에 있다는
사실 자체가 단언이어야 나중에 조용히 빠지지 않는다.

새 단언 (`scanner-zoom.test.js`, 신규 테스트 4건):

| 테스트 | 무엇을 고정하나 |
|---|---|
| r5 ① 순서 | `.scanner-panels` 안의 문자 위치로 상태 < 줌 < 사진 < 안내 < 기타. `order` 선언 금지. i18n 속성·id 이동 후 보존 |
| r5 ② 수치 | 전 뷰포트에서 `ACTION_CONTROLS_HEIGHT ≤ panelVisibleHeight`. 상수 분해(90 · 36 · 184)와 CSS `.scanner-bottom` 선언 대조 |
| r5 ② 증인 | 375×667 · 360×640 에서 **구 순서가 실제로 밀렸음**(326 > 가시 높이) + 새 순서는 안 밀림. 390×844 · 344×882 · 320×980 에서는 구 순서도 안 밀렸음 |

**증인이 비어 있지 않은지 확인했다**: 안내 문구를 다시 앞으로 되돌리는 뮤테이션을
넣으면 r5 ① 의 `photo < guide` 가 뒤집힌다(1334 vs 64). 순서 단언은 공허하지 않다.

`scanLayout()` 반환에 `panelVisibleHeight` 를 더했고, 매트릭스 JSON 행에
`panelVisibleHeight` · `actionControlsHeadroom` · `legacyPhotoBottom` 이 함께 남는다.

## 14. 못 한 것 · 남는 트레이드오프

1. **렌즈 선택(`.camera-picker`)은 짧은 폰에서 여전히 가시 영역 밖이다.** 브리프의 순서
   («기타» 는 안내 문구 뒤)를 그대로 따랐기 때문이다. 실측: 375×667 에서 아래끝 735.33
   vs 패널 626.63, 360×640 에서 722.02 vs 599.63 — **구 순서에서도 밖이었다**
   (구 순서 기준 약 737). 즉 재배열로 **새로 잃은 것은 없다**. 다만 렌즈 선택은 설명이
   아니라 행동 컨트롤이므로, 「행동은 안 잘린다」 를 끝까지 밀려면 안내 문구 앞으로
   올리는 선택지가 남는다 — 브리프가 지정한 순서를 임의로 바꾸지 않았다.
2. **실기기 미검증.** 위는 데스크톱 Chromium 뷰포트 에뮬레이션이다. iOS Safari 의
   `dvh` 거동과 `mask-image` 성능(스크롤 중 합성 비용)은 실기기에서만 확인된다.
3. **네이티브 scroll 이벤트 관측 못 함** (§12 마지막 문단). 렌더 프레임이 안 도는 페인
   환경의 제약이고, 배선·술어는 확인됐다.
4. **`SCANNER_BUILD` 태그 유지** (`2026-08-16.01`). r4 와 같은 이유 — 배포본 식별자는
   레인을 합친 뒤 통합자가 올린다.
5. **`test/output/` 는 gitignore 대상**이다. 이 보고서와 매트릭스 JSON 2종은 추적되지
   않는다(기존 `claude-overlay-guide3.md` 처럼 `git add -f` 로 정본화할지는 통합자 판단).
6. **게이트·디코더·grab 무접촉** (브리프 배제 조건). `cropWindow` · `previewSourceWindow`
   · `renderGuideDots()` · 생성기(루트 `index.html`) 전부 무변경.
