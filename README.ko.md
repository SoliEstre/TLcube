### 타입 H — 실제 3D 큐브 (Y 그룹)

생성기의 Y 선택 아래 **True 3D → H** 는 아이소메트릭 그림 대신 실제 큐브를 만든다. H는 기존 Y와 다른
별도 와이어이며([H 스펙, SPEC §13](SPEC.md#13-h-v2--y-그룹의-실제-큐브-확장)), Y의 안쪽 QR·로케이터·음영은
쓰지 않는다.

- **격자와 면.** 고유 데이터 면 1…6개, 2/3톤, ECC L/M/H, H0…H8 격자(한 변 13…45셀)를 제공한다.
  3면·6면 포맷에서는 면이 세 개씩 한 조(`ZM, XM, YM`, 이어서 `ZP, XP, YP`)로 묶이고, 같은 좌표의 세 모듈이
  base-6 digit 하나를 싣는다. 그래서 한 면만으로는 본문이 완성되지 않는다.
- **용량.** 생성기의 자동 파인더 정책과 3톤에서 ECC-M 순본문은 3면
  **3 / 21 / 45 / 78 / 119 / 123 / 185 / 255 / 333 B**, 6면
  **6 / 42 / 90 / 156 / 238 / 330 / 440 / 510 / 666 B** 다(H0…H8).
- **다른 면 수.** 2·4·5면은 별도로 식별되는 짝/조 패킷([SPEC §13.7](SPEC.md#137-h-v2f--h-v2fc--245개의-고유-데이터-면))이고,
  1면은 단일 패킷([SPEC §13.9](SPEC.md#139-h-v2s--h-v2sc--한-물리면의-단일-패킷))이다. 리더는 스펙대로 구현하면
  되고, 이들을 더해도 기존 포맷의 바이트는 바뀌지 않았다. 1면 H(`mode: 1`)는 XM 안의 두 논리 scan 영역을 한 RS/CRC 패킷으로
  결합하며 H0은 지원하지 않는다. 강한 ECC를 유지한 기본 URL 19 B는 H3(25×25)을 선택한다(2톤 19 B · 3톤 27 B).
- **파인더.** 1…5면 H5 이상과 6면 H7 이상은 면 크기를 늘리지 않고 네 사각 코너 파인더·포맷·기준색을 본문과
  함께 배치한다. 작은 크기는 면 프레임을 유지하고, 이전 프레임 H도 계속 읽는다. 라이브러리 기본
  `finder:'frame'` 의 용량은 이전과 같고, 생성기는 `finder:'auto'` 를 쓴다.
- **배치와 빈 면.** 아이소메트릭(기본)·수평·수직·대칭(2면 전용) 배치가 있다. 빈 면에는 이미지(PNG/JPEG/WebP/SVG)나
  텍스트를 넣고, 텍스트는 여백을 뺀 최대 크기로 가운데 맞춘다. 웹폰트는 고를 때만 Google Fonts 또는 jsDelivr에서
  받는다. 이미지와 텍스트는 현재 페이지에만 남는다.
- **회전.** 화면 기준 X축·Y축(기본)·자이로스코프를 고른다. 자이로스코프는 두 축을 합성한 주기 회전이지 기기 동작
  센서가 아니다. 보정 방식은 회전마다(기본)·면마다·없음이고, 기울임은 0…35도(기본 17.5도)이며 자이로스코프는
  35도 고정이다.
- **영상.** 자동회전을 무음 정사각 MP4(720·1080·1440 px, 24·30·60(기본)·120 fps)로 저장한다. 투명 배경은 투명
  표시 격자·그린(기본)·블루·마젠타로 바뀌며 알파 영상은 아니다. 루프는 «회전마다» 에서 720/속도 초,
  «면마다»·«없음»·자이로스코프에서 360/속도 초마다 닫힌다.
- **내보내기.** PNG/SVG는 전체 데이터 면 시트나 현재 시점만 담는다. Y 그룹의 3D 데이터 섹션은 glTF 2.0 큐브,
  선택색에 가까운 콘크리트의 Minecraft `.schem` 구조물(완성 월드는 아니다), PNG/SVG 전개도를 더 내보낸다.
  이 전개도는 면마다 좌우가 반대인 텍스처 배치라 접어도 판독되지 않는다.
- **만들기용 파일.** 실물 큐브용 종이 도안과 3D 인쇄 파일을 내보낸다(아래). 한 장 전개도로 접어 만든 큐브는
  스캐너로 읽히는 것을 확인했고, 감싸기 스킨·맞대기 판 조각과 3D 프린터로 뽑은 큐브는 아직 실물 스캔으로
  검증하지 않았다.

두께는 일반 종이·카드지·판재·골판지 프리셋이나 잰 값을 쓴다.

## 왜 지금

QR은 1994년의 최선이었다. 흑백 두 값, 정사각 모듈, 큰 파인더는 전부 그 시절 카메라로도 읽히게 하려는
선택이었고, 그 제약 아래서는 미감을 포기하는 게 합리적이었다. 지금은 폰 카메라도, 브라우저 안의 실시간
영상 처리도 여유가 있다. 그 여유를 밀도에 더 쓸 수도 있고 보이는 것에 쓸 수도 있는데, TLcube는 보이는
쪽에 쓴다.

**QR 대체재가 아니다.** 마름모 셀은 모듈 밀도에서 정사각 대비 불리하고, 그건 이미 결론이 난 이야기다.
많이 담아야 하면 QR이 맞다. 노리는 것은 둘이다.

1. **미학** — 그 자체로 전시 가능한 코드
2. **차분 인코딩 강건성** — 데이터가 절대 휘도가 아니라 셀 내 3면의 **상대 순서** 에 실리므로, 단조(monotonic) 톤 커브 변형 — 전역 조명 변화, 감마, 프린터/디스플레이 톤 매핑 — 에 대해 이론상 불변

## 동작 방식

각 육각 셀을 rhombille 타일링으로 3개의 마름모(`T` 상단 · `L` 좌측 · `R` 우측)로 나누고, 세 면의 **상대 휘도 순서** 로 데이터를 싣는다. 3면의 순열은 3! = 6가지이므로 셀 하나가 base-6 digit 하나(log₂6 ≈ 2.585 bit)를 싣는다.

결과물은 *제각각 다른 방향에서 빛을 받은 아이소메트릭 큐브 필드* 처럼 보인다. 인코딩 원리와 비주얼이 일치하는 코드다.

## 렌더러 자유도

데이터 계약은 **면 간 순서**와 **최소 분리폭(Δmin)** 뿐이다. 그 안에서 렌더러는 자유롭다 — 셀마다 절대 휘도를 지터해도, 색을 입혀도, 면 안에 그라데이션을 넣어도, 시간축으로 흔들어도 된다. 상대 휘도 환산 후 순서만 보존되면 된다.

이 자유도가 이 포맷의 핵심 차별점이다.

## 스캐너

[tlscan.estre.so](https://tlscan.estre.so) 스캐너는 카메라나 사진에서 코드를 읽는다. 복호 엔진은 R1과 R2 두
가지이고 기본은 R2다.

- **타입 H 수집.** R2 카메라 프레임이나 연속 사진에서 H 면을 모은다. 필요한 고유 1…6면과 RS/CRC 검증을 모두
  통과한 뒤에만 본문을 보여 주고, 부분면은 마지막 관측부터 90초간 유지한다. 카메라·사진 수집은 서로 분리된다.
  유효 H 부분면을 모으는 동안 Y 처리는 멈추고, H 초기화·만료 뒤에 재개한다.
- **링크.** 검증된 H URL은 TL의 열기 정책을 따르고, 일반 폴백 QR URL은 계속 수동으로 연다. 표시 언어를 바꿔도
  URL을 다시 열지 않는다.
- **일반 QR.** `BarcodeDetector` API를 제공하는 브라우저에서는 R2가 카메라로 일반 QR 코드도 읽는다. QR에서 읽은 링크는
  자동으로 열지 않는다 — 주소를 확인한 뒤 눌러서 연다.
- **가이드.** 카메라 가이드 하단 중앙에 지그재그 면 전개도를 표시하고, 검출된 면의 ID는 관측 원근에 맞춰 잠시
  표시한다. 오래된 관측이나 카메라 좌표가 맞지 않으면 라벨을 숨긴다.
- **후보 과밀.** 어두운 데이터가 후보를 채우는 경우를 줄이도록 최대 512개 성분 중 큰 성분을 우선해 최대
  128개의 윤곽을 검사한다. 면·ECC·CRC 기준은 완화하지 않는다.
- **엔진 전환.** 카메라에서 QR의 정확한 타입 힌트나 검증된 N7로 비Y/H임을 확인하면 임시로 R1로 전환한다.
  자동 전환은 저장된 선택을 바꾸지 않으며, 다시 시작하면 저장된 R2로 돌아온다. 힌트 없는 QR만으로는 타입을
  추측하지 않는다.

합성 영상·워커 검증은 실카메라 인식률이나 모바일 FPS 보증이 아니다. 정지사진 복호 실측은
[소개 페이지의 스캐너 현황](https://tl.estre.so/#scanner-status)에 있다.

## 기술

바닐라 JavaScript와 저장소 내 Node.js 빌드 스크립트를 쓰며 **런타임 의존성은 0**이다. 생성기는 단일 HTML 파일로 묶인다.

내보내기는 **결정적**이다 — 동일 입력이면 PNG/SVG 가 바이트까지 동일하다. 그래서 픽셀은
브라우저 canvas 가 아니라 자체 래스터라이저(`src/raster.js`)가 만들고, PNG 인코딩도 자체
구현(`src/png.js`)이 한다. canvas 는 화면 미리보기, 타입 H 빈 면 글자의 래스터화, 빈 면 이미지의 정규화,
회전 영상의 프레임을 맡는다. 그래서 H 빈 면 글자나 이미지가 들어간 PNG/SVG 와 MP4 는 바이트 동일 보증 밖이다 —
면 글자는 브라우저의 글꼴 렌더링을, 면 이미지는 브라우저의 이미지 디코딩을 거치고, 영상은 프레임을 브라우저의
WebCodecs AVC 인코더로 압축하고 저장소 내 MP4 muxer(`src/cube-video-export.js`)로 묶으므로 바이트가 재현되지 않는다.

인코딩 경로: `encode.js` (페이로드 → RS(GF(211)) 코드워드 → 셀별 digit) → `scene.js`
(digit → 도형 목록) → canvas 미리보기 / `raster.js`+`png.js` / `svg.js`. 렌더 자체 검증은
`verify.js` — 샘플 원판 median 통계로 전 셀의 휘도 순위가 의도한 digit 과 일치하는지
픽셀에서 직접 확인한다.

타입 H 경로: `h-codec.js` (페이로드 → RS(GF(211)) + CRC32C → 면별 digit) → `h-render.js`
(`buildHScene` · `buildHFaceSheet` → 도형 목록) → 같은 미리보기·내보내기 단계. 생성기는 모든 H 코드를
화면에 보이기 전에 다시 복호해 확인한다.

## 스펙

포맷 규범은 **[SPEC.md](SPEC.md)** 다 — 기하·심볼 인코딩·레이아웃·용량·오류 정정·적합성 요건, 그리고 [§13](SPEC.md#13-h-v2--y-그룹의-실제-큐브-확장)의 타입 H 와이어. 용량 수치는 `src/capacity*.js` 와 `src/h-codec.js` 가 계산하고, 와이어 계약은 `test/` 스냅샷이 정본이다. RS/CRC는 무결성 검사이지 암호학적 인증은 아니다.
