# TLcube — TrilLuminance (cube)

[English](README.md) · **한국어**

> 정식 명칭 **TrilLuminance (cube)** · 코드네임 Trilume.
> 육각형을 마름모 3면으로 분할하고, 3면 간 **휘도 순위(순열)** 로 데이터를 싣는 3D 바코드(실은 2.5D).
> 상태: **인코더·디코더·실카메라 스캐너 동작 중** — 브라우저 생성기와 스캐너가 라이브다.

## 무엇인가

각 육각 셀을 rhombille 타일링으로 3개의 마름모(`T` 상단 · `L` 좌측 · `R` 우측)로 나누고, 세 면의 **상대 휘도 순서** 로 데이터를 싣는다. 3면의 순열은 3! = 6가지 → 셀당 base-6 digit 하나(log₂6 ≈ 2.585 bit).

결과물은 *제각각 다른 방향에서 빛을 받은 아이소메트릭 큐브 필드* 처럼 보인다. 인코딩 원리와 비주얼이 일치하는 코드다.

## 왜

**QR 대체재가 아니다.** 마름모 셀은 모듈 밀도에서 정사각 대비 불리하고, 그건 이미 결론이 난 이야기다. 노리는 것은 둘:

1. **미학** — 그 자체로 전시 가능한 코드
2. **차분 인코딩 강건성** — 데이터가 절대 휘도가 아니라 셀 내 3면의 **상대 순서** 에 실리므로, 단조(monotonic) 톤 커브 변형 — 전역 조명 변화, 감마, 프린터/디스플레이 톤 매핑 — 에 대해 이론상 불변

## 렌더러 자유도

데이터 계약은 **면 간 순서**와 **최소 분리폭(Δmin)** 뿐이다. 그 안에서 렌더러는 자유롭다 — 셀마다 절대 휘도를 지터해도, 색을 입혀도, 면 안에 그라데이션을 넣어도, 시간축으로 흔들어도 된다. 상대휘도 환산 후 순서만 보존되면 된다.

이 자유도가 이 포맷의 핵심 차별점이다.

## 타입

| 타입 | 실루엣 | 순 페이로드 (ECC-M) |
|---|---|---|
| **O** | 육각 필드 | 18 / 39 / 65 / 97 B (k = 6 / 8 / 10 / 12) |
| **A** | 정삼각 실루엣 | 31 / 62 / 101 B (k = 6 / 8 / 10) |
| **K** | 육각별(A ∪ 반전 A) | 43 / 86 / 138 B (k = 6 / 8 / 10) |
| **Y** | 단일 아이소메트릭 큐브 | 31 / 98 / 141 B (n = 13 / 21 / 25) |
| **C** | 노치 육각 (타입 O 계열 · 근접 전용) | 130 / 172 / 220 / 255 B (k = 14 / 16 / 18 / 20) |

모든 타입은 데이터 계약을 공유하고 실루엣만 다르다. 전부 **폴백 QR** 을 함께 인쇄할 수
있어서, TL 코드를 못 읽는 리더에게도 최소한의 경로가 남는다.

**K** 는 A 와 그 180° 상을 합집합한 육각별이다. 같은 k 에서 A 보다 셀이 많아 용량이
가장 크고, 여섯 꼭짓점이 검출 앵커를 겸한다.

### True 3D H 큐브 확장

Y 선택 아래 **True 3D → H**는 1…6개의 고유 데이터 면, 2/3톤, ECC L/M/H,
H0…H8(한 변13…45셀)을 제공해요. 생성기의 기본 배치에서 ECC-M 순본문은
3면 **3 / 21 / 45 / 78 / 119 / 123 / 185 / 255 / 333 B**,
6면 **6 / 42 / 90 / 156 / 238 / 330 / 440 / 510 / 666 B**예요.
2…5면 H5 이상과6면 H7 이상은 면 크기를 늘리지 않고 네 사각 파인더·포맷·기준색을 본문과 함께 배치해요.
이전 프레임 H도 계속 읽어요. 라이브러리의 기본 `finder:'frame'` 용량은 이전과 같고,
생성기는 `finder:'auto'`를 사용해요. 기존Y와는 별도 와이어이며 Y 내부QR·로케이터·음영은 적용하지 않아요.
일반 PNG/SVG·스냅샷은 보이는 H 면만 담아요. Y 그룹의 3D 데이터 섹션은 전체 전개도 PNG/SVG,
glTF 2.0 큐브와 선택색에 가까운 콘크리트의 Minecraft `.schem` 구조물을 내보내요(완성 월드는 아니에요).
미리보기 패널에서 화면 기준 X/Y(기본)/합성 회전, 속도와 독립 자세·원근을 조정해요.
새 H의 원근 기본은 4도이며 자동회전이 기본으로 켜져요.
자동 속도(X/Y·자이로)는 H5까지 75·60°/s, H6/H7은 60·45°/s, H8은 50·35°/s예요.
수동 속도는 유지하고 속도 기본값 버튼으로 해상도별 자동 설정을 복원해요.
X/Y 기울임 보정은 0…35도(기본 17.5도)이고 별도 기본값 버튼을 제공해요. 자이로는 35도 고정이에요.
수평/수직 정렬 배치의 해당 회전축에서는 부축 기울임을 끄고 정렬을 유지해요.
H 전용 회전 반사광은 데이터·기준색을 함께 밝히고 흑백 식별부를 보호해요.
H도 코너 QR을 배치할 수 있고 안쪽 QR만 비활성화해요. 자동회전은 720×720/1080×1080/1440×1440 무음 MP4로 저장해요.
코너 QR을 켜도 큐브의 중앙 위치와 장면 크기를 유지해요.
투명 영상 배경은 격자/그린(기본)/블루/마젠타로 대체하며 알파 영상은 아니에요. AVC/MP4 지원 브라우저가 필요해요.
영상 FPS는 24/30/60(기본)/120 카드로 선택해요. 60/120은 WebCodecs AVC가 필요하며 지원하지 않으면 낮은 FPS로 대체하지 않아요.
X/Y와 자이로 모두 부축 움직임까지 360/속도 초마다 닫히는 경로로 자연스럽게 반복돼요.
아이소메트릭(기본)·수평·수직 배치는 논리 면 ID와 표시 위치를 분리해요. 수평/수직은 최대4개의 옆면을 쓰고,
중앙 심지 정렬과 화면 Y/X축 회전을 제공해요. 2면 코드는6면 렌더에서 반대편에도 반복하며 양끝 이미지를 공유해요.
그 외 빈면은 PNG/JPEG/WebP/SVG 이미지·45도 회전·맞추기/늘이기/채우기·배경색을 각각 설정하고, 5면은 한 빈면을 편집해요.
위 용량표는 생성기 자동 파인더 정책의 3톤 3/6면 한정이며, 새 1/2/4/5면은 별도 식별 패킷으로 최신 스캐너가 필요해요.
기존3/6면 바이트는 그대로예요. 이미지는 현재 페이지에만 보관하고
현재시점 출력·전체 전개도·내장 glTF·회전 영상·근접 콘크리트 스키매틱에 포함해요.
새 생성 상태의 마스크 기본은7이며 자동 크기는 강한 ECC 우선 정책을 유지해요. H 미리보기는 가능할 때 면 텍스처를
재사용하는 GPU 경로로 그리고, 정확한 출력용 장면 렌더러와 Canvas 대체 경로도 유지해요.
[H 스펙](SPEC.md#13-h-v2--y-그룹의-실제-큐브-확장-시험판)을 참조해요.
스캐너는 R2 카메라 프레임이나 연속 사진에서 H 면을 모아요. 필요한 고유 1…6면과 RS/CRC 검증 뒤에만
본문을 보여 주고, 부분면은 마지막 관측부터90초간 유지해요. 카메라·사진 수집은 서로 분리돼요.
유효 H 부분면을 모으는 동안 Y 처리는 멈추며, H 초기화·만료 뒤에는 재개해요.
검증된 H URL은 TL의 열기 정책을 따르며 일반 QR URL은 계속 수동으로 열어요. 표시 언어를 바꿔도 URL을 다시 열지 않아요.
카메라 가이드 하단 중앙에 지그재그 면 전개도를 표시하고, 검출된 면의 ID는 관측 원근에 맞춰 잠시 표시해요.
오래된 관측이나 카메라 좌표가 맞지 않으면 라벨을 숨겨요. 어두운 데이터가 후보를 채우는 경우를 줄이도록
최대512개 성분 중 큰 성분을 우선해 최대128개의 윤곽을 검사하며, 면·ECC·CRC 기준은 완화하지 않아요.
카메라에서 QR의 정확한 타입 힌트나 검증된 N7으로 비Y/H임을 확인하면 임시로 R1으로 전환해요.
자동 전환은 저장 선택을 바꾸지 않으며 재실행 시 저장된 R2로 돌아와요. 무힌트 QR만으로는 타입을 추측하지 않아요.
합성 영상·워커 검증은 실카메라 인식률이나 모바일 FPS 보증이 아니에요.

## 기술

바닐라 JavaScript와 저장소 내 Node.js 빌드 스크립트를 사용하며 **런타임 의존성은 0**이에요. 생성기는 단일 HTML 파일로 묶여요.

내보내기는 **결정적**이다 — 동일 입력이면 PNG/SVG 가 바이트까지 동일하다. 그래서 픽셀은
브라우저 canvas 가 아니라 자체 래스터라이저(`src/raster.js`)가 만들고, PNG 인코딩도 자체
구현(`src/png.js`)이 한다. canvas 는 화면 미리보기 전용이다.

인코딩 경로: `encode.js` (페이로드 → RS(GF(211)) 코드워드 → 셀별 digit) → `scene.js`
(digit → 도형 목록) → canvas 미리보기 / `raster.js`+`png.js` / `svg.js`. 렌더 자체 검증은
`verify.js` — 샘플 원판 median 통계로 전 셀의 휘도 순위가 의도한 digit 과 일치하는지
픽셀에서 직접 확인한다.

## 스펙

1면 H(`mode: 1`)는 XM 안의 두 논리 scan 영역을 한 RS/CRC 패킷으로 결합하며 H0은 지원하지 않아요. 강한 ECC를 유지한 기본 URL19B는 H3(25×25)를 선택해요(2톤19B·3톤27B). 빈 면 이미지와 반대면 반복은 3D·내보내기의 공통 표시 매핑을 따르며 기존 2…6면 와이어는 불변이에요. 정확한 배치·용량은 [SPEC §13.9](SPEC.md#139-h-v2s--h-v2sc--한-물리면의-단일-패킷)를 따라요. RS/CRC는 무결성 검사이지 암호학적 인증은 아니에요.

포맷 규범은 **[SPEC.md](SPEC.md)** 다 — 기하·심볼 인코딩·레이아웃·용량·오류 정정·적합성 요건. 본문의 수치 표는 전부 `src/` 의 생성물이고, 와이어 계약은 `test/` 스냅샷이 정본이다.

**디코더만 구현해도 적합 구현**이다 (SPEC §11).
